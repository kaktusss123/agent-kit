# kuber-nagibator: data-plane cluster access

Data-plane clusters have no direct route from the workstation. `kn` bridges that gap: it trades an IAM service key for a token, pulls the cluster kubeconfig from the MK8S gRPC API, deploys a `kubectl proxy` pod on the control plane in namespace `kuber-client-<user>`, keeps a detached local port-forward on 8001 and writes the tunnel kubeconfig `config-b-via-a.yaml` under `kubeconfig_dir` (default `~/kubernetes`). This skill is a workflow adapter over that installed CLI; no tool code lives here.

Two access paths exist and they are not interchangeable: the tunnel kubeconfig reaches one data-plane cluster at a time, while the dev/stage control-plane kubeconfig reaches the control plane directly and never needs a tunnel.

## Mandatory references

- Before the first `kn` command of a session: read `references/kn-reference.md` — exact subcommands and flags, internal-vs-mk8s id resolution and its silent fallback, output shapes, state/config files, timeouts, missing-component diagnoses.
- Before running kubectl through the tunnel, reusing or replacing an active tunnel, cleaning up a failed connect, using the dev/stage control plane directly, or reaching an ingress-only UI: read `references/agent-workflow.md` — explicit kubeconfig per command, tunnel health proof, single-tunnel replacement, failed-connect cleanup, sudo-free ingress access.

## Non-negotiables

- Explicit cluster only. Candidates come from `kn clusters [--env dev|stage]`; the user's input must match a Name, Internal ID or MK8S ID exactly. Ambiguous or unmatched input stops with the candidate list — never pick the closest match, never silently fall back to the last used cluster. Exact match is mandatory whenever that list is available; when the admin API is unavailable (403, network failure), an mk8s id supplied directly by the user is a valid explicit target, never a candidate the agent chose itself.
- Default read-only: `get`, `describe`, `logs`, `top`, `explain`. Mutations — `apply`, `delete`, `patch`, `scale`, `rollout`, `exec`, `edit` — only inside the scope the user explicitly authorized, never as an investigative side effect.
- Control plane is a proxy host, not the target. The dev/stage control-plane kubeconfig from `kn config get environments.<env>.control_plane_kubeconfig` addresses the control-plane cluster; objects the user asked about live in the data-plane cluster behind the tunnel.
- Secrets stay out of output and files: never print or save data-plane kubeconfigs (`cluster-<mk8s-id>.yaml` and the tunnel kubeconfig under `kubeconfig_dir`), `~/.config/kuber-nagibator/state.yaml`, service keys or `KN_SERVICE_KEY_*` values. `kn config show` masks `service_key_secret`; `kn config get` prints raw values — restrict it to non-secret keys such as `kubeconfig_dir` and `environments.<env>.control_plane_kubeconfig`.
- A failed `kn connect` can print the data-plane kubeconfig. Its ConfigMap update passes the whole kubeconfig as a kubectl `--from-literal` argument, and the error handler surfaces that argv. On any connect failure, never quote, paste or `cat` the raw output or the captured log: extract bounded markers only (`grep -m3 -oE 'Failed to [a-z ]+|Error: .{0,120}' <capture-file> | head`), keep the full capture as a local file only, and treat it as secret material.
- Single tunnel slot with an explicit replacement step. Exactly one data-plane tunnel exists at a time (fixed port 8001, one proxy deployment per user namespace), and `connect` never stops the previous port-forward — it starts a new one on the same fixed port. So before any `kn connect` that replaces a tunnel (different cluster or different environment), run `kn disconnect` first, then connect. Silent replacement is dangerous in both directions: within one environment the old port-forward follows the ConfigMap rewrite and starts serving the new cluster, while across environments the old forward keeps port 8001, the new one cannot bind, and the health check can pass against the old process — connect "succeeds" while serving the wrong environment. Check `kn status` first; a healthy tunnel to the same cluster may be reused, but a tunnel owned by another session is only ever borrowed — surface it, never silently replace it, and leave it running afterwards. Replacing someone else's tunnel needs their explicit permission.
- The slot is machine-global, not session-local. Another agent or a human shell may own the running tunnel, and `~/.config/kuber-nagibator/state.yaml` records it; `kn reconnect` and `kn status` read that state, so `kn reconnect`'s "last cluster" is never a valid way to resolve a cluster. Ownership rule: disconnect only a tunnel this session created (or explicitly took over after surfacing it); a borrowed tunnel stays up when your work ends.
- The proxy namespace `kuber-client-<user>` is tunnel infrastructure, not task material: never delete, edit or scale its Deployment/ConfigMap to "fix" access, and never touch it as part of the user's cluster work. Repair goes through `kn connect`, `kn reconnect`, `kn disconnect`. The sole exception is an explicitly user-authorized cleanup of a proxy deployment left running by a failed connect (`references/agent-workflow.md`), never an automatic one.
- When cluster work ends, `kn disconnect` only a tunnel this session created — even after a failed attempt. A borrowed healthy tunnel is left running; stopping someone else's tunnel needs separate explicit permission. Disconnect scales only the deployment named by the state's last environment, so a failed connect to a different environment can leave the target's proxy running — verify and surface it (`references/agent-workflow.md`).
- Do not run `kn ingress`: it needs sudo for `/etc/hosts`, opens a browser and blocks the foreground. Reach ingress-only UIs with a kubectl port-forward plus `curl --resolve` (`references/agent-workflow.md`); if a real browser is required, the user runs that command.
- No unbounded or interactive kubectl in the bash tool: no `logs -f`, no `watch`, no `exec -it` unless the user's task genuinely needs a shell. Bound output with `--tail`, `-o wide`, `--no-headers`.
- Missing prerequisites are reported as exact missing components (`kn`, `kubectl`, `grpcurl`, `~/.config/kuber-nagibator/config.yaml`, credentials). Never improvise a substitute for `kn`, and never edit `~/.config/kuber-nagibator/` yourself — credentials are the user's.

## Flow

1. Preflight: `command -v kn kubectl grpcurl`, then `kn status`. A stale or foreign tunnel is surfaced here, before a two-minute connect attempt: a stale one may be replaced after surfacing; a healthy tunnel owned by another session is borrowed, never silently disconnected.
2. Resolve the cluster: `kn clusters` (add `--env stage`, `--all` for non-RUNNING clusters) and apply the exact-match rule. dev and stage hold different clusters and different credentials, so a cluster missing from one environment is searched in the other before the agent reports it as unknown.
3. Connect: if the running tunnel would be replaced (different cluster or environment) and the tunnel is yours, `kn disconnect` first; if it belongs to another session, stop and get explicit permission before touching it. Then `kn connect <internal-id|mk8s-id> [--env dev|stage]` with a bash timeout of at least 180s (a cold connect takes 2-3 minutes: kubeconfig fetch, proxy rollout wait up to 120s, health-checked port-forward with up to 5 attempts) and its output captured to a local file rather than echoed. `--no-tunnel` retrieves the kubeconfig without a proxy; `--kubeconfig FILE` bypasses the id resolution and MK8S API when those are down.
4. Prove the tunnel is live before real work: `KDIR="$(kn config get kubeconfig_dir)"; KDIR="${KDIR/#\~/$HOME}"; kubectl --kubeconfig "$KDIR/config-b-via-a.yaml" get ns`. A success here is a health check only — it does not prove the cluster identity (different clusters behind one address answer identically); identity comes from step 5. A failure here is a tunnel diagnosis (`references/agent-workflow.md`): first copy the log tail aside, because the next port-forward start truncates `/tmp/kuber-nagibator-tunnel-<port>.log`; then make one reasoned recovery attempt and never retry the same connect blindly.
5. Confirm identity when the CLI resolved something: `connect` prints `Resolved <name> -> mk8s <id>`. If that name is not the cluster the user asked for, stop and re-resolve instead of continuing. When the admin API is unavailable and the mk8s id came straight from the user, no such line is printed — the first `get ns` is then a health check only, and the cluster identity rests solely on the user-supplied id; say so in the record.
6. Do the requested work, read-only unless authorized, with the explicit `--kubeconfig` flag on every kubectl invocation and an explicit `-n` (the tunnel context has no default namespace); use `-A` to locate an object when the namespace is unknown. A tunnel that breaks mid-change leaves the cluster state unknown: re-observe with `get`/`describe` before repeating anything.
7. If the tunnel is yours, `kn disconnect`, then confirm with `kn status`; a borrowed tunnel is left running and the handover is stated. `kn cleanup` only when the user also wants `/etc/hosts` entries and state cleared (it needs sudo).

## Completion

Done means:

- the cluster was resolved by exact match against `kn clusters` with its environment, or by an mk8s id the user supplied directly while that list was unavailable;
- the tunnel was proven live with `get ns` before the first real command, and it served the intended cluster;
- every mutation stayed inside the explicitly authorized scope, and conclusions rest on quoted kubectl output rather than assumption;
- `kn disconnect` ran for a tunnel this session created and `kn status` shows no running tunnel PID — or the reason a tunnel was deliberately left up (borrowed from another session, or a proxy deployment left behind by a failed connect) is stated.
