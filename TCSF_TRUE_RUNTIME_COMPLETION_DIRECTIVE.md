# TCSF true runtime completion directive

## Status of the current checkpoint

The current candidate is a useful implementation checkpoint, but it is not accepted as TCSF.

Preserve the existing work. Do not restart from scratch. Preserve the working real OMP happy path, the canonical catalog, the component probes, the strict reviewer parser, the run-state CAS implementation, and the current evidence root.

This pass is an implementation and exact-conformance pass. It is not another reporting pass.

The normative authority, in descending order, is:

1. `TCSF_IMPLEMENTATION_SPEC.md`.
2. The canonical definitions and hashes derived from that exact specification.
3. This directive, which only states repair order and clarifies evidence requirements.

No prior corrective prompt may redefine an H, E2E, C, or AC identifier.

Do not commit, push, merge, deploy, promote, or replace an accepted runtime. Use isolated fixtures and a candidate-specific runtime root. A targeted sync to a mutable test installation is not promotion, but record it explicitly and preserve rollback data.

## What is already accepted as useful evidence

Retain these results as component or milestone evidence:

- a real OMP implementer changed an isolated worktree;
- deterministic verification executed a real command;
- a fresh OMP reviewer returned a schema-valid result;
- the task reached `ready_for_acceptance` on the simple happy path;
- the candidate bundle can be built and explicitly loaded;
- the report taxonomy no longer relabels old component probes as normative E2Es;
- the report is generated by code and rejects several obvious contradictions;
- run state is read from durable storage and uses revision CAS;
- reviewer payload parsing has adversarial unit coverage;
- filesystem artifact paths reject basic symlink traversal;
- the managed driver records a terminal manifest on the demonstrated happy path.

Do not discard those results. Do not claim they prove stronger properties than they actually exercise.

## Current verdict corrections

Before changing runtime behavior, correct the current generated verdicts. This is not optional reporting work. It prevents later repairs from building on false premises.

### E2E-01

Downgrade the current E2E-01 result to `FAIL` or `NOT_RUN`, depending on the catalog rules, until all of the following are proved in one run:

- the initiating controller process actually exits before the managed driver completes;
- the exit timestamp is observed by the parent process, not written by the controller immediately before process exit;
- an observer starts before terminal completion and observes at least one post-controller, pre-terminal durable state;
- the driver records at least one heartbeat or stage transition after the initiating controller has exited;
- the approved contract artifacts exist, are copied into the frozen task contract, and their hashes and sizes are verified;
- the implementer and reviewer receive the frozen contract, not only its title and acceptance criteria;
- the final execution record is terminal and coherent with the run and driver records;
- the source checkout and every reference repository remain unchanged.

The current harness waits for the controller child before starting the observer and records `controllerExitedAt` inside the controller. That does not prove overlap or controller independence.

### C-01 and C-02

Downgrade C-01 and C-02 until their exact predicates are implemented.

C-01 must prove that the candidate extension loads exactly once. Checking for one command name is insufficient. Record loader identity, registration events, duplicate counts, and the complete command and tool registry.

C-02 must prove that all expected commands and tools are registered exactly once. It must compare the observed registry to an explicit expected registry. Checking only `tcsf_run`, `tcsf_status`, and `tcsf_cancel` is insufficient.

C-01 and C-02 may share low-level loader code, but their oracles must be distinct and match their normative definitions.

## Stage 1: make failure and cancellation safe

This is the first runtime repair. Do not run more long workflows before it is complete.

### 1.1 Fix failed-run persistence

The current `fail()` path creates a failed run without increasing `run.revision`, then calls `saveRun(failed, run.revision)`. The artifact store correctly rejects this because every update must advance the revision.

Fix the path so that:

- failed state increments revision exactly once;
- the failure class and evidence are persisted;
- the run lease is released or explicitly transferred to recovery;
- task state moves to failed with CAS;
- duplicate handling of the same failure is idempotent;
- an exception while persisting failure does not recursively enter the same broken failure path.

Add tests for failures from every stage:

- validate;
- prepare workspaces;
- implement;
- verify;
- review;
- candidate validation;
- waiting state reconciliation.

### 1.2 Fix cancellation

The current cancellation path has the same revision defect and does not prove termination of the driver and all active work.

A successful cancellation must:

1. acquire or reconcile run ownership;
2. persist `cancelling` intent with an advanced revision;
3. interrupt the active agent turn if one exists;
4. stop the execution host process tree;
5. stop the verification process tree if one exists;
6. stop the run driver and await terminal confirmation;
7. release writer and run leases safely;
8. persist execution, run, driver, and task terminal states;
9. record orphan-process inspection evidence;
10. be idempotent when repeated after partial completion.

Test cancellation during implementation, verification, review, waiting, and after terminal completion.

Do not classify cancellation as a generic protocol failure.

## Stage 2: implement a real frozen approved contract

The current import validates packet fields and writes `contract/packet.json`. It does not verify or freeze the referenced spec and verification artifacts.

Implement the approved-contract boundary before claiming AC-01.

### 2.1 Import requirements

For every artifact in the approved packet:

- resolve the source through an explicitly permitted import root or connector;
- reject absolute-path escape, traversal, and symlink escape;
- read the bytes;
- verify the declared size;
- verify the declared SHA-256 hash;
- copy the bytes into the task-owned `contract/` directory;
- record the copied path, size, hash, and import timestamp in a frozen manifest;
- make the copied contract create-only and immutable for the task lifetime;
- compute and persist one contract snapshot hash over the manifest and artifact bytes.

The import must fail before workspace preparation if any artifact is missing, stale, malformed, or mismatched.

### 2.2 Runtime use of the contract

The implementer must receive an unambiguous reference to the frozen snapshot and enough content to work without access to the original approval source.

The reviewer must evaluate:

- the actual Git diff relative to the approved base SHA;
- the frozen contract snapshot;
- the verification results;
- prior reviewer findings when applicable.

The reviewer must not rely on the mutable packet object or on only the title and acceptance criteria.

Add tests for:

- valid frozen import;
- missing artifact;
- wrong size;
- wrong hash;
- source artifact mutation after import;
- attempt to overwrite a frozen artifact;
- symlink and traversal import;
- implementer prompt references only task-owned frozen artifacts;
- reviewer receives the same snapshot hash.

Update E2E-01 fixture to use real artifact files and valid hashes.

## Stage 3: make run ownership real

Revision CAS prevents a stale revision from overwriting a newer revision. It does not by itself establish one active controller.

### 3.1 Enforce the run lease

Every state-changing operation must validate:

- lease token;
- holder identity;
- acquisition time;
- expiry;
- expected run revision.

A controller may renew only its own unexpired lease. It may not silently rewrite another holder's identity.

Expired-lease takeover must use a recorded reconciliation protocol. Record the prior holder, process identity, last heartbeat, reason for takeover, and the first reconciled revision.

Persist the current lease token in driver state. A driver may advance only the run for which it holds the accepted token.

### 3.2 Recover stale storage locks

The short CAS lock file must contain structured metadata:

- PID;
- process start token;
- host identity;
- acquired time;
- target run or task;
- expected revision.

A stale lock may be removed only after proving that its owner is gone or that an approved expiry rule applies. Corrupt lock data must fail closed and require deterministic reconciliation. It must not block a task forever or be deleted blindly.

### 3.3 Make events durable and ordered

Event sequence numbers must be monotonic per run. Two different events may not share the same sequence.

Append must be serialized and crash-tolerant. The reader must tolerate or repair one truncated final line without ignoring corruption in earlier lines.

Add append and replay tests with concurrent writers, process death, truncated final records, and duplicate event IDs.

## Stage 4: prove initiating-controller independence correctly

The initiating process must not retain a live child reference that keeps it alive until the driver exits.

Use a documented launch strategy that allows the driver to outlive the initiating process. Depending on Bun behavior, this may require a detached process, `unref`, a small launcher, or another public process API. Probe the installed Bun behavior first.

The exact E2E-01 harness must be controlled by a parent test process:

1. parent starts the initiating controller;
2. controller imports the contract, starts the run, writes the driver identity, and exits;
3. parent observes the controller's actual OS exit;
4. parent starts or already has an observer running;
5. observer sees a non-terminal state after controller exit;
6. driver records a heartbeat or stage transition after controller exit;
7. the workflow later reaches `ready_for_acceptance`;
8. parent proves all child processes stopped;
9. final task, run, driver, execution, session, and repository records agree.

Record OS-observed timestamps and process start tokens. A timestamp written by the exiting process is not sufficient.

Do not mark AC-04 PASS until this exact timeline is proved.

## Stage 5: make execution lifecycle and worker recovery coherent

### 5.1 Terminal execution records

On successful completion, failure, cancellation, handoff, and replacement, persist the execution status and timestamps.

At `ready_for_acceptance` no execution may remain durably `running` unless the contract explicitly requires a live retained session. If a logical session remains resumable, distinguish that from a running host process.

Add explicit fields or states for:

- logical session resumable;
- host running;
- foregrounded;
- stopped;
- succeeded;
- failed;
- cancelled;
- replaced.

### 5.2 Turn idempotency

`turn-intent.json` and `turn-complete.json` are useful, but recovery must use them.

Before sending a prompt, persist a unique logical turn ID and content hash. After transport loss:

- determine whether OMP accepted or completed that turn;
- do not resend an ambiguous prompt blindly;
- resume the same session when possible;
- reconcile session history and persisted frames;
- send a replacement prompt only when the prior prompt is proved not applied;
- record any unavoidable ambiguity as a blocker, not as a routine retry.

### 5.3 Worker replacement

Implement E2E-05 with a real OMP worker:

- complete and persist at least one turn;
- start the next turn;
- kill the OMP host process;
- detect loss through lifecycle evidence;
- start a replacement host;
- resume the same logical session;
- prove no duplicate prompt was applied;
- continue the workflow.

### 5.4 Timeouts and transport evidence

Move turn and silence timeouts into task, role, model, and stage policy. The default must tolerate known slow first-token behavior.

Silence timeout must reset on meaningful lifecycle activity, not only assistant text.

Await stderr draining and artifact persistence before closing a transport. Preserve raw or lossless protocol evidence required by H-02.

## Stage 6: complete the decision path

The factory must let the implementer raise a critical semantic decision even though autonomous child OMP currently starts without global extensions, skills, or rules.

Probe and choose a session-bound mechanism. Preferred order:

1. a minimal per-execution control extension or RPC channel bound to task, run, execution, and session identity;
2. a public structured-output mechanism with strict schema;
3. a strict terminal control envelope with one protocol-repair turn.

Do not add a global unbound tool that any agent can use to mutate arbitrary runs.

A valid decision request must be produced by the factory and include a validated resume stage. The resume stage must be one of the allowed state-machine stages, not an arbitrary string cast.

When a decision is requested:

- persist the request;
- persist the run transition to `waiting_for_decision`;
- stop the active driver loop without marking it failed;
- leave no active model turn or busy polling loop;
- allow the initiating process to be absent;
- accept exactly one non-conflicting resolution;
- update request status or link the immutable resolution explicitly;
- resume from the recorded stage without repeating completed work.

Implement exact E2E-04 with process restart.

## Stage 7: repair foreground handoff and writer leases

### 7.1 Persisted lease release

Writer lease release must work after process restart. Do not rely on a process-local map.

Release must:

- load the persisted lease;
- compare host ID, owner, token, and generation;
- remove only the exact current lease;
- reject an old owner attempting to release a newer lease.

Corrupt lease JSON must fail closed and enter reconciliation. Do not delete it and grant a new writer.

Renew long-lived leases while a turn or operator session remains active. A lease may not expire silently while its owner is still writing.

### 7.2 Same-session continuity

The continuity nonce must be inserted into the pre-handoff logical session history before the controller releases ownership. The operator must retrieve it from the resumed session history, not from a launch instruction that could be copied into another session.

A valid handoff must prove:

- same logical session ID before, during, and after;
- nonce exists in pre-handoff history;
- operator resumes that session;
- concurrent controller input is rejected;
- operator performs a turn;
- nonce is consumed once;
- operator lease is released through persisted-token validation;
- controller reacquires a new lease;
- autonomous execution continues in the same session.

Implement exact E2E-06. A local lease component probe is not a substitute.

## Stage 8: close Git and repository safety gaps

### 8.1 Scope matching

Replace prefix matching with path-segment-aware matching. `src/**` must not match `src2/file`.

Normalize separators and reject absolute paths, traversal, NUL bytes, and ambiguous platform forms.

### 8.2 Parse Git status correctly

Handle porcelain `-z` rename and copy records correctly. Add fixtures for spaces, Unicode, rename, copy, staged delete, staged add, intent-to-add, and nested untracked directories.

### 8.3 Detect committed mutations

Compare each repository and worktree to the approved `baseSha`, not only to current `HEAD` status.

An agent-created commit must remain visible to:

- scope validation;
- review diff generation;
- source and reference repository integrity checks.

The reviewer must receive the full diff from approved base to the current worktree, including staged, unstaged, untracked, and committed changes.

### 8.4 Safe restoration

For isolated clean fixtures, restoration must correctly handle:

- staged modifications;
- staged additions;
- staged deletions;
- committed unauthorized changes;
- untracked files;
- untracked directories;
- symlink writes;
- traversal attempts.

Do not use `git checkout -- file` as proof that staged state was restored. Verify index, worktree, HEAD/base SHA, and untracked state after restoration.

If safe restoration cannot be proved, fail closed and preserve the fixture for inspection.

Implement exact E2E-07. Attempt every required mutation. A passive check is not evidence.

## Stage 9: make verification process-safe

Replace the current single-process timeout with managed process-tree execution:

- unique process group or equivalent child-tree ownership;
- stdout and stderr streamed to durable artifacts;
- bounded in-memory summaries;
- explicit timeout state;
- SIGTERM grace period;
- SIGKILL escalation;
- wait for all descendants;
- deterministic final exit metadata;
- no inference of timeout solely from exit code 137 or 143.

Use the configured default timeout when no per-run override exists. Do not ignore `defaultTimeoutMs`.

Add a verification-runner contract test that starts a child with a resistant grandchild and proves cleanup.

## Stage 10: make candidate isolation real

### 10.1 Correct self-change detection

A task is a self-change when it can modify:

- TCSF core, ports, adapters, bindings, runner, tests, or conformance code;
- extensions used by TCSF;
- active TCSF skills or agents;
- runtime configuration contracts;
- candidate validation infrastructure.

Do not detect self-change only when one writable-scope string equals `extensions/tcsf` or the repository root ends with that suffix.

Use canonical repository roots plus path-aware writable scopes. Add positive and negative tests for the actual dotfiles layout.

### 10.2 Isolate the candidate

Candidate validation must use separate:

- HOME;
- TCSF_HOME;
- session directory;
- OMP config root;
- fixture repositories;
- artifact and report roots;
- process identities.

The stable parent bundle and state must be immutable for the candidate run. Record full-tree hashes, not only `index.ts`.

Candidate code must not write parent reports, parent task manifests, active runtime files, or parent session storage. Use a narrow parent-owned result channel.

### 10.3 Exact C-01 and C-02

C-01 proves one candidate extension load and no duplicate TCSF registration.

C-02 compares the complete expected TCSF command and tool registry to the observed registry and rejects missing, duplicate, or unexpected lifecycle registrations.

### 10.4 Complete C-03 through C-10

Each candidate runner must execute its own normative behavior. A unique source file that calls a shared loader-only function does not satisfy a distinct scenario.

The stable parent evaluates the result from external evidence. The candidate does not grade itself.

Integrate the candidate pack into the normal self-development stage, rather than leaving it only as an external test script.

## Stage 11: strengthen the conformance oracle

The current validator is a useful structural validator. It is not yet a behavioral evidence validator.

### 11.1 Enforce catalog requirements

For every PASS, validate the catalog's exact:

- required actors;
- required process boundaries;
- required preconditions;
- required observations;
- required evidence files;
- linked hypotheses;
- linked acceptance criteria.

Do not accept report booleans such as `realOmpBoundary: true` as proof. Read and validate the evidence content.

### 11.2 Bind evidence to the executed source

The scenario runner must record the source-tree hash at execution time. The report generator must read that hash from immutable scenario evidence.

Do not overwrite old evidence with the current source hash during report generation.

Reject evidence whose execution hash differs from the evaluated source, unless the report explicitly classifies it as historical and does not use it for PASS.

### 11.3 Validate runner semantics

Checking that a runner source contains the string `E2E-XX` is insufficient.

Use scenario-specific machine-readable observations and independent predicates. The validator need not interpret arbitrary code, but it must verify the required evidence objects and their relationships.

Examples:

- E2E-01 must contain an OS-observed controller exit, later driver heartbeat or transition, and a pre-terminal observer record;
- E2E-05 must contain the same session ID, two distinct host identities, one logical prompt ID, and no duplicate application;
- E2E-06 must contain session-history nonce evidence, concurrent denial, lease generations, and successful reacquisition;
- C-01 must contain one loader identity and exactly one TCSF registration set;
- C-02 must contain complete expected-versus-observed registry comparison.

### 11.4 Generate acceptance predicates, not mappings

Each AC needs a predicate over exact static checks, scenario results, and evidence content.

Do not map a list of AC IDs to one scenario verdict. The scenario is evidence. The AC predicate decides whether that evidence is sufficient.

Compute `overall` from mandatory AC verdicts. Do not hardcode `overall: FAIL` or later `overall: PASS`.

### 11.5 Make the bundle independently verifiable

The final evidence bundle must contain or immutably reference:

- normative spec bytes;
- catalog bytes;
- source manifest and hash;
- runner sources;
- command evidence;
- scenario evidence;
- report generator version;
- validator version.

Avoid absolute machine-specific paths as the only references. Support relocating the acceptance root and validating the archive on another machine with compatible tooling.

## Evidence rules

Do not create placeholder scenario directories.

For every executed scenario, store:

- exact runner source;
- source-tree hash captured before execution;
- normative definition hash;
- command and sanitized environment;
- actors and process start tokens;
- timestamps observed by an external parent where lifecycle ordering matters;
- task, run, driver, execution, session, lease, and decision records;
- events and raw or lossless protocol evidence;
- repository state before and after;
- verification output artifacts;
- independent oracle result;
- cleanup and orphan inspection;
- explicit PASS or FAIL.

Use `NOT_RUN` only when the scenario did not execute. Use `FAIL` when it executed and violated its oracle. Use `BLOCKED_BY_DEPENDENCY` only when a named failed dependency makes execution invalid.

Component probes remain useful, but never count them as exact E2E or candidate scenario results.

## Working behavior

Continue autonomously through routine implementation, isolated process launches, fixture creation, tests, restarts, candidate isolation, adversarial checks, and bounded repairs. These actions are already authorized.

Do not stop because acceptance remains red after an intermediate stage. Persist the failure, repair the responsible layer, and rerun the smallest affected test before continuing.

Do not spend another pass only modifying the report, catalog, or validator. Runtime repairs and exact scenario execution are the primary deliverables of this pass.

## Stop and escalation rules

Stop only when one of these is true:

- a required test would irreversibly modify a non-fixture repository or accepted runtime;
- no public or safely probed OMP mechanism can preserve same-session foreground continuity, and every approved fallback has failed with evidence;
- no idempotent recovery rule can distinguish whether a lost OMP turn was applied, and continuing risks duplicate destructive work;
- candidate isolation cannot prevent mutation of stable state under any approved local boundary;
- safe restoration cannot preserve pre-existing user changes and no fail-closed alternative satisfies the contract;
- the approved architecture must change rather than the implementation;
- an external credential, provider outage, or operator-only action blocks every safe fallback.

An escalation must include:

- exact failed invariant and IDs;
- durable evidence paths;
- preferred path attempted;
- every safe fallback attempted;
- concrete options;
- recommendation;
- effect on architecture, safety, and named ACs.

Do not request authorization for ordinary E2Es, candidate scenarios, process restarts, test fixtures, long-run simulation, or repairs described here.

## Completion report

Generate the final report only after the exact suite has run or a valid escalation condition has been reached.

The report must distinguish:

- static conformance;
- component probes;
- hypotheses;
- exact real OMP E2Es;
- candidate scenarios;
- long-run mechanics;
- acceptance criteria.

Every PASS must be produced by a scenario-specific predicate over evidence captured by the executed source revision.

The implementation is accepted only when every mandatory AC passes. Until then, report the checkpoint honestly and continue safe independent work.
