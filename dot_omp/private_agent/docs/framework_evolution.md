# D1.5: превратить `/dev` из чистого оркестратора в владельца задачи

Работаем в репозитории `omp-cmux-dotfiles`.

Предыдущий этап уже выполнен: `dev-orchestrator` и `spec-analyst` больше не являются skills. Они перенесены в явные prompt templates `/dev` и `/spec`.

На этом этапе меняем только поведение `/dev`.

## Зачем

Текущий `/dev` унаследовал старую модель `dev-orchestrator`: основной агент владеет процессом, но намеренно не пишет продуктовый код и делегирует реализацию subagent'ам.

Мы больше не считаем это хорошим default.

Для обычной связной инженерной задачи отдельный чистый оркестратор часто только добавляет:

* передачу контекста;
* лишние model turns;
* дополнительные failure points;
* более сложную координацию;
* необходимость управлять subagent'ами там, где один агент мог закончить работу самостоятельно.

Новая модель:

```text
/dev
  ->
основной агент владеет всей задачей
  ->
сам исследует, проектирует, реализует, проверяет и исправляет
  ->
делегирует только там, где делегация дает конкретное преимущество
```

Это всё ещё управляемый development workflow, но основной агент теперь является development owner, а не диспетчером других агентов.

## Что изменить

Изучи текущий `prompts/dev.md` и связанные reusable skills.

Перепиши `/dev` так, чтобы основной агент имел право самостоятельно:

* читать и исследовать код;
* принимать локальные инженерные решения;
* изменять продуктовый код;
* запускать проверки;
* исправлять найденные проблемы;
* создавать необходимые промежуточные артефакты;
* доводить задачу от запроса пользователя до проверенного результата.

Удали или перепиши инструкции, которые требуют делегировать реализацию только ради разделения ролей.

В частности, не должно остаться правила вида:

```text
main agent never writes code
implementation must be delegated
main agent only coordinates
```

## Когда использовать subagents

Subagent не является обязательным этапом workflow.

Основной агент делегирует работу только когда может назвать конкретную причину, почему отдельный контекст или параллельное исполнение лучше прямой работы в текущей сессии.

Хорошие причины:

1. Есть действительно независимые части работы, которые можно безопасно выполнять параллельно.
2. Нужен независимый свежий взгляд, например сложный review или verification, где self-review недостаточно.
3. Нужно независимо исследовать большой объём материала, который засорит основной context.
4. Нужно сравнить несколько реальных альтернатив или провести независимые эксперименты.
5. Специализированный reusable skill или agent имеет явно подходящую компетенцию.

Не считать достаточной причиной:

* "так устроен workflow";
* "implementer должен быть отдельным";
* "reviewer всегда должен быть отдельным";
* "это большая задача";
* "можно распараллелить хотя бы теоретически".

Предпочитать одного владельца для тесно связанной работы.

Если несколько частей меняют один и тот же код или требуют постоянного обмена свежим контекстом, это обычно один workstream, а не повод создавать несколько агентов.

## Verification

Не ослаблять требование проверки результата.

После изменений основной агент должен получить реальное evidence того, что задача решена.

Используй существующие reusable capabilities, в частности:

```text
skill://verification-design
skill://change-verification
skill://project-verification
```

где они подходят.

Но отдельный verifier-agent теперь не обязателен.

Для дешёвых объективных проверок основной агент может сам:

* запустить тесты;
* выполнить typecheck;
* собрать проект;
* воспроизвести bug;
* проверить CLI/API/UI;
* изучить runtime output.

Отдельный независимый verifier оправдан, когда проверка:

* требует инженерного суждения;
* имеет большой blast radius;
* легко подвержена confirmation bias автора;
* проверяет сложное пользовательское поведение;
* служит независимым acceptance review.

Не запускай отдельного агента только для повторения одной очевидной команды.

## Review

То же правило относится к review.

Не делать независимый code review обязательным для каждого изменения.

Использовать отдельный review там, где он добавляет новую информацию.

Например:

* сложное изменение контрактов;
* concurrency;
* security-sensitive change;
* большой blast radius;
* архитектурная перестройка;
* неоднозначная реализация;
* пользователь явно просил review.

Для маленького локального изменения не создавать reviewer только ради соблюдения ритуала.

Существующие skills `code-review`, `blast-radius` и другие остаются reusable capabilities. Не копируй их содержимое в `/dev`.

## Структура работы

Не превращай `/dev` в новый подробный state machine.

Prompt должен задавать несколько устойчивых принципов, а не список обязательных ролей.

Пример желаемой логики:

```text
understand the requested outcome
        ↓
ground in the actual repository
        ↓
choose the smallest coherent approach
        ↓
work directly or delegate where it clearly helps
        ↓
implement
        ↓
verify the resulting behavior
        ↓
repair if evidence shows a problem
        ↓
finish only when the requested outcome is actually satisfied
```

Допускаются любые возвраты назад, дополнительные исследования и прототипы, если задача этого требует.

Не пытайся заранее перечислить все допустимые переходы.

## Сохрани сильные стороны текущего `/dev`

При переписывании не потеряй полезные свойства существующего workflow:

* основной агент остаётся владельцем исходной пользовательской задачи;
* сначала понимает реальное состояние репозитория;
* не задаёт пользователю вопросы, ответ на которые можно получить из кода, документации или эксперимента;
* держит scope под контролем;
* декомпозирует только когда это помогает;
* проверяет результат против исходного запроса, а не только против локальных тестов;
* после неудачной проверки исправляет текущее состояние, а не начинает работу заново;
* не заявляет completion без evidence;
* использует reusable skills вместо копирования их инструкций;
* делает handoff только когда это действительно требуется.

## `/spec`

На этом этапе `prompts/spec.md` не менять, кроме случаев, когда там есть прямая устаревшая ссылка на старую модель `/dev`.

Не переносить новую свободу product-code implementation в `/spec`.

`/spec` по-прежнему занимается discovery, design и specification. Disposable prototypes допустимы по его текущим правилам, но реализация продукта не является его задачей.

## Не делать на этом этапе

Не добавляй:

* workflow runtime;
* `workflowz`;
* `eval.js` или `eval.py`;
* extension commands;
* hooks;
* verification completion gate;
* obligations/evidence database;
* SHA-bound verification state;
* persistent workflow state;
* новую систему ролей;
* новую сущность coordinator;
* автоматический repair loop.

Мы намеренно сначала проверяем более простой agentic workflow.

## Проверка изменения

После изменения проведи статическую проверку prompt и небольшой реальный smoke test с установленным OMP.

Нужно подтвердить:

1. `/dev` по-прежнему корректно запускается.
2. User arguments доходят в workflow.
3. Основной агент понимает, что имеет право самостоятельно редактировать код.
4. Он не считает запуск implementer-subagent обязательным.
5. Он всё ещё считает verification обязательным перед completion.
6. Он умеет решить простую связную задачу без subagents.
7. В задаче с очевидной независимой исследовательской частью он всё ещё может разумно использовать subagent.
8. `/spec` не изменил своё назначение.

Если есть возможность сделать два коротких smoke-сценария, используй:

### Сценарий A: один агент

Маленькое изменение в disposable repo, которое один агент может полностью понять, реализовать и проверить.

Ожидание: `/dev` не создаёт subagent без причины.

### Сценарий B: оправданная делегация

Задача с двумя независимыми областями исследования или с отдельной сложной проверкой.

Ожидание: `/dev` может делегировать, но делает это потому, что это полезно, а не потому, что workflow требует роль.

Не подгоняй prompt под smoke tests. Они проверяют естественное поведение.

## Критерий результата

После D1.5 `/dev` должен означать:

> "Возьми ответственность за эту development task и доведи её до проверенного результата. Работай сам по умолчанию. Используй других агентов там, где отдельный контекст, независимость или параллелизм реально улучшают результат."

А не:

> "Управляй командой агентов, но сам код не трогай."

Сам prompt должен стать проще текущего, если удаление orchestration ceremony позволяет это сделать.

Не добавляй текст только ради сохранения прежнего размера файла.

Не коммить изменения без отдельной просьбы.

В конце дай короткий отчёт:

* что изменилось в семантике `/dev`;
* какие обязательные делегации были удалены;
* какие причины для делегации остались;
* как теперь устроены verification и review;
* результаты двух smoke tests;
* были ли обнаружены причины, по которым чистый orchestrator всё-таки необходим для обычной `/dev` задачи.
