# ADR-0001: standalone Pi-first boundary for agent-kit

Status: Accepted
Date: 2026-09-13

## Context

`agent-kit` начинался как набор общих assets для нескольких agent harnesses. В репозитории существовали отдельные слои для Pi, OMP и OpenCode, а общую логику предполагалось выносить в shared abstractions.

Эта модель оказалась преждевременной. Реально развиваемый runtime сейчас один, Pi. Попытка поддерживать общий слой до появления второго настоящего consumer увеличивала количество adapters, bindings и compatibility policy, не улучшая сам Pi workflow.

Одновременно у `agent-kit` появляется другой возможный consumer. В будущем локальные agent runs должны запускаться удалённо через agent node, control plane и web UI. Task tracker также может инициировать работу и получать результаты.

Эти системы не должны становиться обязательной частью локального agent framework.

Пользователь должен иметь возможность установить `agent-kit`, запустить Pi в локальном repository и получить полный development workflow без control plane, tracker, daemon или сетевого сервиса.

Это решение фиксирует границу до проектирования deterministic task lifecycle, durable runs и headless execution.

## Decision

### 1. `agent-kit` является самостоятельным локальным framework

`agent-kit` владеет всеми возможностями, необходимыми для локальной работы агента.

К ним относятся:

* skills и workflow policy;
* Pi prompts и extensions;
* model classes и subagent orchestration;
* structured `ask` и `needs_input`;
* task identity и task workspace;
* worktree management и mutation protection;
* Git operations, checkpoints и commits;
* push и PR/MR operations, когда workflow или пользователь их запрашивает;
* verification и review capabilities;
* task artifacts, включая specifications и ADR;
* будущий local durable execution runtime;
* будущий headless способ запуска этого же runtime.

Эти возможности не могут зависеть от внешнего control plane, task tracker или remote-management service.

Практический инвариант:

> Если удалить весь будущий control-plane stack и отключить сеть, должны исчезнуть только функции удалённого управления. Локальная работа с агентом должна продолжать работать.

### 2. Pi является текущим runtime, а не реализацией generic harness interface

`agent-kit` сейчас проектируется для Pi.

Мы не вводим заранее:

* `Harness`;
* `HarnessAdapter`;
* `PiAdapter`;
* общий multi-harness runtime;
* отдельные `shared/`, `runtimes/`, `bindings/` или аналогичные слои ради потенциальных будущих harnesses.

Pi-specific contracts допустимы в skills, references и extensions.

Host-independent код можно отделять внутри конкретного capability, когда это уменьшает связность или упрощает тестирование. Само наличие такого кода не является причиной создавать общий framework package.

Если позже появится реальный второй runtime, например OpenCode, первый port должен быть downstream integration. Общую abstraction следует выделять только после того, как два работающих consumer покажут, какие различия действительно нужно скрывать.

### 3. Semantic policy и deterministic mechanics остаются разными слоями

Skills отвечают за решения, которые требуют semantic judgment модели.

Extensions отвечают за операции и гарантии, которые должны выполняться кодом.

Prompt templates связывают существующие capabilities в workflow и не должны копировать policy из skills или deterministic logic из extensions.

Пример:

```text
skill:
    решить, нужен ли checkpoint
    выбрать semantic scope
    выбрать commit message

extension:
    проверить target repository
    stage exact paths
    запустить hooks
    запретить unsafe commit
    вернуть structured result
```

Это разделение существует ради надёжности agent workflow, а не ради portability между harnesses.

### 4. Capability не должен зависеть от своего orchestrator

Низкоуровневый capability не должен знать, каким high-level workflow или controller он используется.

Направление зависимости должно идти от orchestration к capability.

Например:

```text
RepoOwner / subagents
        |
        v
task-workspace
```

`task-workspace` может регистрировать tools и guards, но не должен знать, что его загрузил RepoOwner profile, как controller проверяет readiness или куда controller отправляет события.

Controller может проверять observable capability и применять к нему дополнительный protocol.

Эта же модель должна использоваться для новых orchestration layers.

### 5. Task, Run и Pi Session являются разными понятиями

Эти сущности нельзя объединять в один lifecycle.

#### Task

Task описывает durable development scope.

С ним связаны:

* identity;
* branch;
* task workspace;
* repository worktrees;
* specifications и другие durable artifacts.

Task может существовать независимо от активного agent process.

Одна Task может выполняться несколькими Runs.

#### Run

Run является одной попыткой выполнения работы.

Будущий Run должен иметь собственный lifecycle и execution state, например:

```text
running
needs_input
completed
failed
cancelled
interrupted
```

Точная state machine и persistence model определяются отдельным решением.

Run не является частью Git identity Task и не должен использовать branch/worktree state как замену execution state.

#### Pi Session

Pi Session является runtime-specific механизмом выполнения.

Run может использовать Pi Session, но identity и lifecycle Run не должны определяться существованием конкретного Pi process или session file.

Сегодня полноценной durable Run abstraction ещё нет. Это ограничение текущей реализации, а не повод считать Task или Pi Session той же сущностью.

### 6. Durable artifacts остаются локальными

Specifications, ADR, reports и другие task artifacts должны иметь локальное canonical representation внутри `agent-kit` task environment.

Будущий control plane может:

* обнаруживать artifacts;
* индексировать их;
* показывать в UI;
* передавать ссылки или копии внешнему tracker.

Control plane не становится владельцем canonical artifact.

Например, если `SPEC.md` является canonical specification для Task, отсутствие control plane не должно делать specification недоступной или невалидной.

### 7. `ask` и `needs_input` являются локальной execution semantics

Agent должен иметь один semantic способ сообщить, что без решения продолжать работу нельзя.

Концептуально:

```text
agent
  |
  v
ask
  |
  v
needs_input
  |
  v
answer
  |
  v
same execution continues
```

Способ доставки вопроса является отдельной проблемой.

В interactive Pi ответ может приходить из TUI.

В будущем headless Run ответ может прийти через local control interface от agent node и control plane.

Agent logic не должен различать эти случаи и не должен знать, существует ли control plane.

Отсутствие usable backend должно приводить к явному fail-closed outcome, а не к выдуманному ответу или продолжению работы при неизвестном решении.

### 8. Observability и control являются разными каналами

`agent-events` предназначен для observational telemetry.

Telemetry допускает:

* best-effort delivery;
* потерю событий;
* отсутствие acknowledgement;
* отсутствие retry;
* failure sink без влияния на agent execution.

Поэтому telemetry нельзя использовать как authoritative источник execution state или как transport для операций, correctness которых зависит от доставки.

Через telemetry нельзя строить:

* reliable `needs_input`;
* cancel;
* resume;
* reconnect;
* replay;
* authoritative Run state;
* durable remote execution protocol.

Warp является telemetry consumer.

Другие telemetry consumers могут использовать ту же модель событий, если им подходят такие guarantees.

Future remote control требует отдельного reliable interface.

Улучшение observability subagents не меняет это решение, пока observability остаётся наблюдением и не становится владельцем execution state или control semantics.

### 9. Headless execution принадлежит `agent-kit`

Headless execution не является функцией control plane.

В будущем `agent-kit` должен уметь локально запустить тот же workflow без interactive TUI и предоставить machine-readable способ:

* start;
* inspect status;
* receive execution events;
* answer `needs_input`;
* cancel;
* obtain outcome и artifacts.

Interactive и headless execution не должны превращаться в две отдельные реализации development workflow.

Оба режима должны использовать один local runtime и одинаковые task, worktree, Git, verification и agent capabilities.

Точная форма интерфейса, например process protocol, JSONL, RPC или local socket, данным ADR не определяется.

### 10. Remote management является внешним слоем

Будущая система удалённого управления находится над `agent-kit`.

Целевая зависимость:

```text
Task tracker
     |
     v
Control plane
     |
     v
Agent node
     |
     v
local agent-kit interface
     |
     v
agent-kit
     |
     v
Pi
```

Допустимое направление зависимости:

```text
external systems -> agent-kit
```

Запрещённое направление:

```text
agent-kit -> control plane
agent-kit -> task tracker
agent-kit -> remote node service
```

Agent node является adapter между remote control protocol и локальным `agent-kit`.

Он не должен самостоятельно реализовывать task workspace, Git policy, commits, verification или agent workflow.

Control plane также не должен обходить `agent-kit` и напрямую управлять его Pi extensions или внутренними files.

External management components по умолчанию должны развиваться отдельно от репозитория `agent-kit`. Изменение этой границы требует отдельного архитектурного решения.

## Consequences

### Positive

Локальный framework остаётся полезным независимо от того, будет ли когда-либо закончен control plane.

Разработка remote management не определяет внутреннюю архитектуру agent workflows.

Pi-specific improvements можно делать напрямую, не поддерживая speculative compatibility layer.

Task/worktree/Git semantics имеют одного владельца и не дублируются между local и remote execution.

Появляется понятная точка для будущей интеграции. External systems должны использовать local execution interface, а не внутренние Pi extensions.

### Trade-offs

`agent-kit` сознательно не предоставляет generic multi-harness API.

Если появится второй runtime, его первая интеграция может содержать некоторое дублирование до того, как появятся данные для хорошей общей abstraction.

Полноценный local Run runtime и headless interface пока отсутствуют. Этот ADR определяет их ownership и constraints, но не реализацию.

Task workspace уже durable, execution пока session-scoped. До реализации durable Run crash/restart semantics остаются ограниченными текущим Pi runtime.

## Rejected alternatives

### Сделать control plane владельцем execution workflow

Отклонено.

В этом варианте local agent development начинает зависеть от внешней инфраструктуры, а Git/worktree/verification logic либо переезжает в control plane, либо дублируется.

### Использовать `agent-events` как protocol для remote execution

Отклонено.

Telemetry contract специально допускает loss и не имеет acknowledgement или retry. Усиление этого interface до reliable protocol смешало бы observability и control.

### Сразу восстановить multi-harness abstraction

Отклонено.

Сейчас есть один реальный runtime. Абстракция была бы построена на предположениях о будущих consumers вместо наблюдаемых различий.

### Считать Task, Run и Pi Session одной сущностью

Отклонено.

Task живёт дольше одного запуска. Один Task может требовать discovery, implementation, repair и review runs. Pi process или session является механизмом выполнения, а не durable task identity.

### Хранить canonical task state во внешнем tracker или control plane

Отклонено.

Это нарушило бы standalone requirement и сделало бы локальный workflow зависимым от внешней availability.

## Verification and enforcement

Архитектурная граница должна быть видна не только в документации.

Текущие и будущие tests должны защищать следующие свойства:

1. Active repository layout не возвращает retired multi-harness layers без отдельного решения.
2. Capability modules не получают reverse dependency на high-level orchestrators. В частности, `task-workspace` остаётся self-contained и не зависит от `subagents`.
3. `agent-events` сохраняет telemetry-only failure semantics. Ошибка sink не должна ломать agent execution.
4. Local task/worktree/Git workflow не требует external control services.
5. Future headless workflow использует те же local capabilities, что interactive Pi, а не повторяет их во внешнем daemon.
6. Future agent node взаимодействует с `agent-kit` через стабильный local execution interface и не импортирует внутренние extension modules для выполнения workflow.
7. Future external tracker integration может быть полностью удалена без потери local development capabilities.

Если новое изменение требует нарушить один из этих пунктов, его нельзя маскировать локальным workaround. Нужно явно пересмотреть это ADR.

## Out of scope

Этот ADR не определяет:

* deterministic task lifecycle и его state machine;
* hook model;
* точную модель durable Run;
* Run persistence и crash recovery;
* headless protocol;
* agent-node transport;
* control-plane API;
* remote authentication;
* scheduling между nodes;
* task tracker schema или конкретный tracker;
* automatic task pickup;
* OpenCode или другой второй runtime;
* конкретную структуру будущего external-control repository.

Эти решения принимаются отдельно внутри установленной здесь границы.

## Follow-up

Следующее архитектурное решение должно определить deterministic local task lifecycle.

После него можно проектировать durable local Run и headless execution, уже не возвращаясь к вопросу о том, кому принадлежат эти capabilities.

>
> Note (2026-09-16): оба открытых здесь вопроса закрыты. Durable Run — ADR-0004: отдельный Run runtime не вводится. Headless execution — ADR-0005: используется штатный `pi --mode rpc`, собственный daemon, Run runtime, event journal или RPC-протокол не вводятся. Формулировки «будущий» о durable Run и headless запуске (§1, §5, §9) следует читать через эти два решения; новые решения их не переоткрывают.
