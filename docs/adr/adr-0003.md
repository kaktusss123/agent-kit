# ADR-0003: verification of the settled repository state upon successful RepoOwner done

Status: Accepted
Date: 2026-09-13

## Context

ADR-0002 defined the candidate commit as the verification boundary and left a "Required follow-up": minimal Pi enforcement of the settled state at the boundary of successful completion. It specifically required:

1. Repository upon successful completion is in an expected, settled state.
2. Runtime collects Git facts itself instead of trusting the model's self-report.

The current `workspace_agent` accepts a fresh `report_result` and completes the run as `done` without checking anything mechanical: a model could report `done` on a dirty tree, without a commit, or even after deleting the worktree — and Main would learn about it only from the report's own words.

The question is the minimum enforcement that doesn't build a workflow engine.

> Note (2026-09-14): after this ADR was accepted, the separate `workspace_agent` surface was merged into the unified `subagent` tool. The same contract — readiness validation, enforced deadline, terminal envelope, settled-state verification on `done` — is now implemented by the workspace run layer of `subagent op=spawn workspace=...` (see `skills/git-task/references/repo-owners.md`). The original tool names below are kept as historical record.

## Decision

### 1. Runtime checks the settled state at the `done` boundary

When the child settles with a fresh envelope with `status: "done"`, the workspace layer — after the child is stopped (retire), so the state doesn't change during the check — reads the repository state with git:

* the workspace is still an accessible git repository;
* the repository has a current HEAD;
* the working tree is clean (porcelain status is empty; untracked non-ignored files count as dirty, ignored ones — build artifacts, caches — do not).

If all three conditions pass, `done` is accepted.

If any condition fails, `done` is not accepted: the run settles as `blocked` with a reason of the form `done_rejected_dirty_worktree: ...` or `done_rejected_unreadable_git_state: ...`, `child_may_have_mutated_repo: true`. The report envelope in this case is not returned as a trusted `result`. Fail closed: an unreadable git state is not treated as clean.

### 2. Terminal result is supplemented with objective Git facts

Every terminal outcome of `workspace_agent` (`git_facts`) contains:

* branch;
* HEAD SHA;
* list of dirty paths (staged/unstaged).

The facts are read by the runtime from the repository, not taken from the model. Main doesn't ask which commit was produced and whether anything was left uncommitted — the terminal result already contains this.

### 3. Enforcement point is one

The entire check lives in one place — in the settlement of the workspace layer, on the fresh `done` envelope path. No new state machine, no hooks, no `verification` framework, no evidence storage. `report_result`, guards, and `checkpoint_commit` remain unchanged.

### 4. `partial` and `blocked` don't require clean state

If the envelope reports `partial` or `blocked`, clean state is not required — these statuses exist precisely to report unfinished work. Git facts are still attached to the terminal result (best effort).

## Out of scope

Consciously not done and not guaranteed:

* evaluation of adequacy of the RepoOwner's selected checks — remains a semantic judgment per ADR-0002 §12;
* proving that a commit was created via `checkpoint_commit` (raw `git commit` is not forbidden);
* extension of the bash guard to sed, interpreters, and redirects — the guard remains protection from typical accidental errors, not a security boundary;
* proving the origin of dirty state or identifying "who" left it behind;
* sandbox and prohibition of dangerous commands;
* storage of verification evidence and linking test runs to SHA;
* protection from a TOCTOU race: after the check, the tree can theoretically be changed by someone else — after the child stops this requires a third party, not a model.

## Consequences

Successful `done` is no longer just the model's word: it means a readable repository with HEAD on a clean tree, verified after the agent stopped. A dirty tree after "verification" (ADR-0002 §9) stops slipping through as a success. The price is three git invocations per `done` settlement and two machine reasons, which Main handles using the existing "inspect + repair" scheme.
