# ADR-0002: candidate commit как граница финальной верификации

Status: Accepted
Date: 2026-09-13

## Context

`agent-kit` использует Pi как agent runtime и сознательно оставляет модели свободу в том, как выполнять инженерную работу.

ADR-0001 зафиксировал разделение между:

* semantic judgment в skills;
* deterministic mechanics и hard guarantees в extensions;
* task, Run и Pi Session как разными понятиями;
* локальным `agent-kit` и будущими внешними control-plane слоями.

Следующий вопрос — насколько детерминированным должен быть development workflow.

Ранее рассматривалась возможность представить разработку как явную state machine:

```text
analyze
-> implement
-> verify
-> review
-> repair
-> reverify
-> finish
```

Такой подход был отклонён.

Реальная разработка редко следует одной последовательности. Агент может:

```text
исследовать
-> изменить код
-> запустить focused test
-> обнаружить другой контракт
-> продолжить исследование
-> исправить реализацию
-> снова проверить
-> создать checkpoint
-> исправить ещё один дефект
```

Жёсткое sequencing не увеличивает надёжность настолько, насколько ограничивает сильную модель и усложняет runtime.

Более подходящая модель:

```text
agent decides HOW to do the work

framework decides:
- какие операции разрешены;
- какие hard invariants нельзя нарушить;
- какое observable состояние требуется на границе завершённой работы.
```

Часть этой модели уже реализована.

`task-workspace` детерминированно обеспечивает managed worktrees и mutation protection.

`checkpoint_commit` обеспечивает exact staging, secret-path protection, hook execution, primary-checkout protection и другие механические гарантии commit operation.

При этом verification всё ещё в основном является semantic policy. RepoOwner обязан проверять изменение и возвращать structured report, но отсутствует простая и однозначная граница, к какому именно состоянию кода относится финальная verification.

Рассматривалась возможность ввести собственные repository fingerprints, generic evidence store, obligations graph и explicit verification claims.

Эта модель была отклонена как преждевременное усложнение.

Git уже предоставляет подходящий immutable identifier состояния кода — commit SHA.

Поскольку task branches являются рабочей историей и итоговые изменения обычно попадают в target branch через squash merge, промежуточные candidate commits не обязаны быть красивой публичной историей.

## Decision

### 1. Development workflow остаётся agent-driven

`agent-kit` не вводит общую state machine для `/dev`.

Framework не требует фиксированного порядка:

```text
implement -> verify -> review -> repair
```

и не хранит универсальную текущую engineering phase.

RepoOwner может свободно:

* исследовать repository;
* редактировать код;
* запускать focused checks;
* возвращаться к исследованию;
* исправлять найденные проблемы;
* делать промежуточные проверки;
* использовать TDD;
* создавать дополнительные checkpoints, если они полезны.

Детерминизация применяется к границам и опасным операциям, а не к полному пути агента.

### 2. Candidate commit является immutable границей финальной проверки

Когда RepoOwner считает изменение кандидатом на завершение, текущее coherent состояние repository должно быть зафиксировано commit'ом.

Концептуально:

```text
implement / test / repair freely
          |
          v
candidate commit C1
          |
          v
final verification of C1
```

Commit SHA является идентификатором candidate revision.

Не вводится отдельный repository snapshot fingerprint для этой цели.

Candidate commit создаётся через существующий безопасный commit mechanism `checkpoint_commit`.

Candidate commit:

* находится в managed task worktree;
* находится на task branch;
* содержит explicit intended path set;
* проходит commit hooks по действующему contract;
* не означает автоматически, что изменение полностью verified;
* не означает автоматически readiness к push или merge.

### 3. Итеративная verification и финальная verification различаются

RepoOwner должен иметь возможность запускать проверки в любой момент разработки.

Например:

```text
edit
-> unit test
-> edit
-> typecheck
-> repair
-> unit test
```

Такие проверки являются development feedback и помогают сформировать candidate.

Финальная verification отличается только тем, что выполняется для уже созданного candidate commit.

Таким образом:

```text
development checks
    помогают получить candidate

candidate commit
    фиксирует exact revision

final verification
    принимает или отвергает этот candidate
```

Framework не запрещает запускать те же проверки до commit.

Напротив, быстрая verification до candidate commit остаётся нормальной инженерной практикой.

### 4. RepoOwner выбирает repo-local verification

Framework не содержит project-specific verification workflow.

Он не знает заранее, что repository нужно проверять через:

```text
pytest
go test
npm test
mvn test
```

или любую другую конкретную команду.

RepoOwner отвечает за выбор достаточной локальной verification.

Для этого он может использовать `verification-design` и repository evidence:

* project scripts;
* Makefile;
* CI configuration;
* test layout;
* contribution documentation;
* nearby precedent;
* характер фактического изменения.

Например:

```text
uv run pytest tests/foo/test_parser.py
uv run mypy src/foo
```

или:

```text
pnpm test parser
pnpm typecheck
```

Runtime не пытается самостоятельно оценить semantic adequacy выбранного набора проверок.

### 5. Main и RepoOwner имеют разные verification responsibilities

RepoOwner отвечает за локальную verification изменённого repository.

Main отвечает за task-level synthesis и final review результата RepoOwner.

Main может дополнительно выполнить integration или cross-repository verification, когда этого требует характер задачи.

Например:

```text
repo A local verification PASS
repo B local verification PASS

но task меняет контракт A -> B

=> Main может потребовать integration verification
```

Такая дополнительная проверка не является обязательным отдельным stage для любой задачи.

Для простого single-repo изменения локальной verification RepoOwner и review Main часто достаточно.

### 6. Separate verifier/reviewer не является обязательной частью workflow

Наличие отдельного verification agent не является гарантией качества само по себе.

Fresh-context verifier или reviewer используется только тогда, когда независимость реально полезна.

Типичные причины:

* security-sensitive изменение;
* concurrency;
* сложный публичный или межсервисный контракт;
* большой blast radius;
* сложная integration/E2E acceptance;
* архитектурное изменение;
* подозрительный или неоднозначный результат;
* explicit user request.

Не следует создавать отдельного verifier только потому, что workflow концептуально содержит шаг verification.

### 7. Verification failure создаёт новый candidate

Если финальная verification candidate commit `C1` не прошла, RepoOwner исправляет repository.

После любой repair, изменяющей candidate state, `C1` больше не является актуальным кандидатом.

Создаётся новый candidate commit:

```text
C1
 |
 verification FAIL
 |
 repair
 |
 v
C2
 |
 verification
```

Verification результата `C1` нельзя считать verification `C2`.

Это свойство получается естественно из Git identity и не требует отдельной evidence invalidation system.

### 8. Изменение verified commit создаёт новую revision

После успешной verification нельзя изменять содержимое verified candidate и продолжать считать старую verification действительной.

Например:

* amend;
* rebase;
* новый commit поверх candidate;
* generated-file update;
* manual repair;
* конфликт resolution.

Все эти операции создают другое repository state.

Новое состояние требует новой финальной verification перед successful RepoOwner completion.

Framework не обязан моделировать причины invalidation отдельно. Достаточно различия commit SHA.

### 9. Финальная verification не должна оставлять незаписанное изменение candidate

После final verification repository должен оставаться в согласованном состоянии.

Если verification command:

* форматирует файлы;
* обновляет generated sources;
* изменяет lockfile;
* модифицирует tracked files;
* создаёт необходимые для candidate untracked artifacts,

результат verification нельзя считать финальным подтверждением старого candidate.

Изменённое состояние должно быть рассмотрено RepoOwner, при необходимости зафиксировано новым candidate commit и проверено снова.

### 10. Structured RepoOwner report остаётся основной границей owner -> Main

Не вводится отдельный generic Evidence API.

RepoOwner продолжает завершать работу через существующий structured report с полями уровня:

```text
status
summary
changed_scope
verification
gaps
contract_conflicts
```

Verification report описывает выполненные проверки и их результаты.

Runtime может дополнить terminal result объективными Git facts, которые не требуют model judgment, например:

```text
HEAD
branch
dirty state
```

Модель не должна вручную утверждать факты, которые runtime может получить непосредственно из Git.

### 11. Successful RepoOwner completion относится к committed settled state

Для task mutation successful owner outcome должен описывать состояние, которое:

* находится в managed task worktree;
* зафиксировано candidate commit;
* не содержит незаписанных изменений, относящихся к выполненной работе;
* прошло выбранную RepoOwner финальную verification после создания соответствующего candidate.

Точная механика enforcement определяется отдельно при проектировании Pi hooks/extensions.

Этот ADR фиксирует semantic contract, а не конкретный event-handler API.

### 12. Verification adequacy остаётся semantic judgment

Framework сознательно принимает ограничение:

RepoOwner может выбрать недостаточно сильный test.

Runtime не пытается автоматически доказать, что:

```text
pytest tests/foo.py
```

достаточен для конкретного изменения.

Это задача engineering judgment и review.

Надёжность обеспечивается сочетанием:

* `verification-design`;
* repository conventions;
* RepoOwner reasoning;
* structured verification report;
* final review Main;
* отдельной independent verification там, где риск её оправдывает.

Если реальные прогоны покажут повторяемый failure mode, где модели систематически заявляют verification без фактического выполнения или выбирают заведомо недостаточную проверку, для этого failure mode может быть добавлен отдельный deterministic mechanism.

До появления такого evidence дополнительная инфраструктура не вводится.

### 13. Push и PR/MR не входят в verification boundary

Candidate commit не означает permission на внешние side effects.

Commit, verification, push и PR/MR остаются разными понятиями.

Концептуально:

```text
candidate committed
        !=
candidate verified
        !=
candidate pushed
        !=
PR/MR created
```

Push policy и PR/MR automation определяются отдельными capabilities и решениями.

Этот ADR не делает push или publication обязательной частью `/dev`.

### 14. Intermediate commits допустимы

Task branch является рабочей историей выполнения задачи.

Наличие последовательности:

```text
C1 candidate
C2 repair
C3 repair
C4 final candidate
```

является допустимым.

Framework не должен создавать сложную историю только ради ceremony, но и не должен избегать полезных immutable checkpoints ради красоты branch history.

При squash merge промежуточная task history не переносится в target branch.

Поэтому возможность использовать commit SHA как простую verification boundary считается более ценной, чем стремление заранее получить идеальную commit history.

## Consequences

### Positive

Git SHA становится естественным immutable identifier candidate state.

Не нужен отдельный working-tree fingerprint.

Не нужен generic evidence store.

Не нужен obligations graph.

Не нужна большая workflow state machine.

Crash или session interruption оставляет последний candidate в понятном Git state.

Fresh-context reviewer или verifier может работать с конкретным immutable commit.

Repair автоматически создаёт новую revision и естественно инвалидирует verification старой revision.

Future headless или durable execution сможет ссылаться на те же commit identities без изменения engineering semantics.

Framework сохраняет свободу сильной модели и добавляет deterministic mechanics только на узкой границе завершённого изменения.

### Trade-offs

Task branch может содержать candidate commits, которые позже оказались нерабочими.

Это считается приемлемым: task branch является рабочей историей, а не release history.

Commit больше не обязательно означает "эта версия уже полностью verified".

Нужно различать:

```text
candidate commit
```

и:

```text
verified candidate
```

Semantic adequacy verification остаётся ответственностью модели и review, а не runtime.

Некоторые repositories могут иметь hooks, которые уже выполняют значительную часть verification во время commit. Финальная verification после commit всё равно полезна как explicit acceptance конкретного SHA, но не обязана бессмысленно дублировать каждую hook check.

## Rejected alternatives

### Большая development state machine

Отклонено.

Жёсткая последовательность плохо соответствует реальному engineering workflow и создаёт orchestration complexity без доказанной пользы.

### Generic obligations engine

Отклонено на текущем этапе.

Несколько hard invariants ещё не оправдывают общий runtime для obligations, dependencies, invalidation и completion solving.

Такая abstraction может быть выделена позже, если несколько реальных независимых mechanisms покажут общий контракт.

### Working-tree fingerprint как revision identity

Отклонено.

Fingerprint HEAD, tracked diff и untracked state технически реализуем, но создаёт собственную snapshot semantics поверх уже существующего Git.

Candidate commit предоставляет более простой immutable identifier.

### Generic `verify()` tool

Отклонено на текущем этапе.

Framework не нуждается в отдельной оболочке для каждой test command только ради регистрации evidence.

Обычные agent tools и существующая verification discipline достаточны, пока реальные failures не покажут обратное.

### Explicit `verification_complete()` claim

Отклонено.

Дополнительный claim object и evidence references увеличивают protocol surface, хотя semantic ownership verification уже находится у RepoOwner и Main.

Structured terminal report является достаточной границей на текущем уровне зрелости.

### Обязательный separate verifier для каждого изменения

Отклонено.

Независимая verification полезна только когда она предоставляет отдельный signal. Ритуальный verifier увеличивает latency, стоимость и orchestration complexity.

### Verification только до commit

Отклонено как единственная authoritative модель.

После проверки working tree остаётся отдельная операция commit, которая может изменить состояние через hooks, generated files или другие mechanics.

Commit-first boundary позволяет verification относиться к конкретному immutable SHA.

## Required follow-up

> Resolution (2026-09-14): этот follow-up закрыт ADR-0003, и она сознательно выбрала самый простой enforcement. Runtime механически гарантирует только settled состояние на границе успешного завершения — доступность Git, наличие HEAD, чистое рабочее дерево — и сам собирает объективные Git facts. Связь «final verification ↔ candidate commit» runtime механически не доказывает: порядок `candidate commit -> final verification -> done` остаётся semantic policy RepoOwner (§11–§12), закреплённой в skill policy, а не runtime gate. Достраивать generic evidence store, obligations engine или runtime verification engine здесь не требуется — этот выбор сделан явно.
