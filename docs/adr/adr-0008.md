# ADR-0008: task-workspace runtime в Claude Code — CLI + skills-directory plugin, RepoOwner без переноса протокола

Status: Accepted (guard неактивен на машинах с allowManagedHooksOnly, см. «Проверка на живой сессии»)
Date: 2026-10-12
Основание: A9 (`docs/specs/a9-claude-code-host.md`), ADR-0007
Проверенная версия Claude Code: 2.1.281 (документация code.claude.com на 2026-10-12)

## Context

ADR-0007 дал Claude Code skills и правила, но не runtime. A9 требует того же task workflow без второй копии policy, без MCP и без правки real files пользователя (`~/.claude/settings.json`).

## Decision

1. **CLI вместо инструментов (W1).** `agent-kit task <op> '<json>'` (`extensions/task-workspace/cli.ts`, исполняется `bun`) — вторая обёртка над тем же ядром, что Pi extension. Параметры — ровно параметры Pi-инструментов, статусы те же; паритет закреплён тестом, который вызывает обе обёртки.
2. **Доставка hooks и CLI (W4, U1) — skills-directory plugin.** `claude-code/plugin` ставится инсталлером symlink'ом `~/.claude/skills/agent-kit`. Claude Code грузит такие plugins на месте (`<name>@skills-dir`), без marketplace и без записи в `settings.json`; `bin/` plugin'а попадает в PATH Bash, `hooks/hooks.json` активен, пока plugin включён. `uninstall` снимает ссылку — hooks уходят вместе с ней. Вариант «пользователь вручную подключает hooks-файл в `settings.json`» отклонён: нарушает приёмку W4 («без ручного редактирования»). Marketplace из локального пути отклонён: регистрация пишет в `settings.json` и `known_marketplaces.json`, т.е. в чужие real files.
3. **Guard (W3).** `SessionStart` → `agent-kit task hook session-start` дописывает в `CLAUDE_ENV_FILE` те же четыре переменные, что Pi spawnHook (`AGENT_TASK_ROOT`, `AGENT_KIT_REAL_GIT`, `AGENT_KIT_POLICY_RUNTIME`, `AGENT_KIT_POLICY`) и shim первым в PATH. `PreToolUse` (`Edit|Write|MultiEdit|NotebookEdit`) → тот же `guardManagedWriteTarget`. Нет окружения/`bun` — fail open. CLI вычищает shim из собственного PATH, чтобы его flows (worktree add в source repo, checkpoint commit) шли через настоящий git — та же изоляция, что у Pi-процесса.
4. **«Дом» исполнителя (W2, D4).** RepoOwner-протокол не переносится. Исполнитель — Agent-tool субагент, которому Main передаёт абсолютный путь managed worktree как единственный дом (пути абсолютные, Bash как `cd <wt> && …`). Защита от ухода в primary checkout — guard из п.3 (hooks и env наследуются субагентами). Объективные факты результата Main читает сам: `agent-kit task status` (branch, HEAD, dirty), `done` принимается только при новом HEAD и чистом дереве. Вопрос исполнителя → `blocked`-отчёт, Main продолжает того же агента через `SendMessage`.

   Отклонено:
   - `isolation: worktree` — создаёт отдельный worktree Claude под `.claude/worktrees/` на своей ветке от default branch, не task worktree; reuse невозможен без `WorktreeCreate`.
   - `WorktreeCreate` hook — глобальная подмена создания worktree для всех сессий пользователя (включая `claude --worktree`), вход несёт только `name`, не branch/source; `WorktreeRemove` не может отказать в удалении (Q1: reuse технически возможен, защита от удаления — нет).
   - `EnterWorktree(path)` для Main — переносит cwd, права записи и project config всей сессии (нарушает «cwd Main не меняется» в `/spec`), один worktree на сессию (Q3), требует подтверждения вне `.claude/worktrees/`. Остаётся возможным ручным выбором пользователя для однорепозиторной задачи; встроенные проверки изоляции Claude Code тогда дополняют guard.
5. **References per host (W5).** `SKILL.md` общий; `references/claude-code/*.md` — привязка тех же контрактов к CLI и субагентам; `SKILL.md` направляет в Claude Code читать их дополнительно. `metadata.hosts: pi` у `git-task`/`git-commit` снят. Механизм выбора — текст, а не инсталлер: так он не мешает OpenCode (U4).

## Consequences

- Ответы на Q1–Q4: Q1 — не используется (см. п.4); Q2 — не нужен, исполнитель работает в сессии Main с её instructions; Q3 — multi-repo = несколько субагентов, у каждого свой абсолютный путь, guard работает по реальному cwd git; Q4 — settled state проверяет Main через `agent-kit task status`, `needs_input` → `SendMessage`, дедлайна нет (размер задания, `TaskStop`).
- Гарантии слабее Pi: нет принудительного дедлайна, нет readiness handshake, settled-state проверка — обязанность Main, а не runtime. Если это окажется недостаточным, следующий кандидат — `SubagentStop` hook, отказывающий при грязном дереве worktree из отчёта.
- Claude Code-сессия в primary checkout'е репозитория с managed worktrees больше не может править его tracked-файлы — как в Pi.

## Проверка на живой сессии (2026-10-12, рабочий Mac, Claude Code 2.1.281)

- Подтверждено: skills-directory plugin, установленный symlink'ом, загружается (`agent-kit@skills-dir · loaded`), его hooks видны (`claude plugin details`).
- U2 подтверждён: managed settings содержат `"allowManagedHooksOnly": true`; hooks plugin'а не вызываются (трассировка пуста), `/hooks`: «Only hooks from managed settings run here». На таких машинах п.3 (guard) не действует; `bin/` plugin'а в PATH Bash тоже не появился, CLI доступен через `~/.local/bin/agent-kit`.
- Sandbox Bash не даёт писать в task root (`~/.agent-kit/tasks`) и ходить в сеть с учётными данными (`git push` по SSH, `gh`).

Решение до пересмотра корпоративной политики: кодовые guard'ы не обходим и не заменяем. Hooks остаются в plugin'е (включатся сами, если политику ослабят). Пробел закрыт текстом: `references/claude-code/task-workspace.md` («Without the guard», «Sandboxed Bash») — сессия проверяет `$AGENT_KIT_POLICY`, без guard'а маршрутизацию соблюдает модель; commits только через `agent-kit task commit` (его отказ для primary checkout и секретов — код CLI, политика его не трогает); операции над task root в sandbox'е отдаются пользователю командой `!`. Отложенные варианты: встроенная изоляция `EnterWorktree` (O1), shim через профиль shell (O2), hooks в managed settings (O3).

## Не проверено

- `CLAUDE_ENV_FILE` в Bash субагентов (неактуально, пока hooks запрещены).
