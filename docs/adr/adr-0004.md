# ADR-0004: crash recovery опирается на Pi session + Git/worktree; отдельный durable Run runtime сейчас не вводится

Status: Accepted (amended by AK-03: a pid-based cross-process lease now exists, see below)
Date: 2026-09-14

## Context

Ранее рассматривалась отдельная durable `Run` abstraction с собственным состоянием, persistence и восстановлением после падения Main-сессии. ADR-0001 (§5) оставил этот вопрос открытым, зафиксировав только концептуальное различие Task, Run и Pi Session.

Живое исследование на Pi 0.85.1 показало, что для текущего development workflow это не нужно: существующие примитивы Pi и Git уже дают достаточно состояния, чтобы восстановить работу после аварийного завершения Main.

## Verified behavior

Живыми экспериментами на Pi 0.85.1 подтверждено:

- завершённые сообщения Main сохраняются Pi в session JSONL;
- после `SIGKILL` Main сессию можно восстановить (resume) и продолжить диалог с работающими расширениями;
- in-flight ответ или tool result может потеряться;
- дочерний RepoOwner (`pi --mode rpc`) после смерти Main получает EOF stdin и завершается — в том числе при `SIGKILL` Main;
- при штатном завершении по EOF child корректно останавливает свои выполняющиеся bash-процессы;
- состояние кода в managed worktree сохраняется;
- новый RepoOwner без transcript предыдущего способен восстановить текущее состояние по Git, файлам, `SPEC.md` и тестам и продолжить работу.

## Decision

Не вводить сейчас:

- durable `Run` runtime;
- собственное хранилище состояний run;
- PID/process registry;
- reconnect к старому RepoOwner;
- replay/event journal;
- orphan reaper;
- recovery state machine;
- сохранение transcript субагентов поверх Pi.

Модель восстановления:

```text
Main crash
    ->
Pi session resume
    ->
старый RepoOwner завершается
    ->
worktree/Git/task artifacts остаются
    ->
Main запускает нового RepoOwner
    ->
новый RepoOwner исследует фактическое состояние и продолжает
```

Главные durable источники состояния разработки:

- Pi Main session — разговор Main;
- Git/worktree — состояние реализации;
- task artifacts (`SPEC.md`, ADR и т.п.) — долговечный контекст задачи.

RepoOwner process и его внутреннее runtime-состояние считаются одноразовыми.

Концептуальное различие `Task`, `Run` и Pi Session из ADR-0001 сохраняется, но не требует наличия отдельной реализованной сущности Run. Отдельная Run abstraction может появиться позже, только если конкретный consumer — например headless execution или control plane — докажет необходимость собственного идентификатора и состояния запуска.

## Limitations

Зафиксированные ограничения принятой модели:

- падение до первого завершённого assistant message может оставить Main вообще без session-файла — это текущее поведение Pi;
- in-flight работа может быть потеряна;
- две независимые живые Main-сессии технически могут одновременно запустить RepoOwner на одном worktree: к crash recovery это не относится, cross-process lock сейчас не вводится;
- поправка AK-03 (extensions/task-workspace, owner-lock): вышесказанное «не вводится» частично снято — dispatch RepoOwner'ов сериализован pid-based lease (`<taskRoot>/.owners/*.json`, liveness через pid + start time), а `teardown_task_repo` / `remove_task_lane` отказывают статусом `owner_active` при живом или непроверяемом владельце. ADR-0004 в остальном (никакого durable Run, recovery через Pi session + Git/worktree) сохраняет силу; lease защищает только dispatch/удаление, но не произвольную запись в worktree через bash/edit (см. ограничения AK-03).
- если будущая автоматическая система сможет перезапускать Main практически мгновенно, предположение «старый RepoOwner успевает завершиться» нужно будет перепроверить.

## Rejected alternatives

### Отдельный durable execution runtime

Отклонён как преждевременная сложность: текущая система уже восстанавливает полезное состояние через существующие Pi/Git примитивы. Ни один наблюдаемый failure mode не потребовал новой инфраструктуры.
