# Рабочий процесс и инструменты Pi

## От спецификации к реализации

В Pi и Claude Code отправьте `/spec <описание задачи>`, затем, после
согласования требований, `/dev`. Это сообщения агенту, не команды оболочки.
В Codex используйте `$spec` и `$dev`.

В режиме `/spec` основная сессия определяет задачу, создаёт или переиспользует
worktree и исследует код в нём. Навыки исследования помогают установить факты,
а `specification` оформляет требования, решения и проверки в `SPEC.md`
каталога задачи. Продуктовый код в этом режиме не меняется.

В режиме `/dev` основная сессия использует спецификацию и назначает по одному
субагенту-владельцу на каждый изменяемый репозиторий. Независимые работы могут
идти параллельно. Владелец реализует изменение, проверяет его и создаёт коммит.
Основная сессия читает фактическое состояние Git, решает, нужен ли независимый
ревьюер, и передаёт исправления новому владельцу. Протокол описан в
[`git-task`](../skills/git-task/SKILL.md) и его `references/`.

## Задачи и рабочие деревья

Задачу определяет ветка пользователя или ветка на основе тикета, например
`feat/KEY-123_short_slug`. Без тикета агент спрашивает разрешение на работу
без него. Тикет и `base_ref` агент не придумывает: если база не задана явно,
её выбирает runtime.

Каталог задачи находится в `~/.agent-kit/tasks/`; корень можно изменить
через `AGENT_TASK_ROOT`. Он содержит управляемые worktree всех участвующих
репозиториев, `SPEC.md` и дополнительные артефакты задачи. Имя каталога
выводится из имени ветки. Основной checkout остаётся нетронутым, даже если
в нём уже есть незакоммиченные изменения.

Владелец репозитория, RepoOwner, меняет только один назначенный worktree.
Основная сессия координирует, проверяет и интегрирует, но не правит репозитории
задачи сама. Дополнительный worktree той же задачи, lane, нужен для настоящей
второй ветки, например backport или hotfix, не для отдельного запуска тестов.

Коммит через `checkpoint_commit` включает ровно перечисленные пути,
запускает Git hooks, отклоняет основной checkout и пути, похожие на секреты.
Сырой `--no-verify` запрещён; отправка коммита не выполняется автоматически.
Владелец может отчитаться `done` только после проверки закоммиченного
кандидата. Последующая правка требует нового коммита и финальной проверки.
[Граница проверки](adr/adr-0002.md), [проверка результата владельца](adr/adr-0003.md).

Git shim в `PATH` блокирует изменяющие Git-команды в основном checkout
репозитория с управляемыми worktree, `--no-verify` и перенаправление через
`--git-dir`/`--work-tree`. Отдельная проверка запрещает инструментам записи
менять отслеживаемые файлы основного checkout. Это защита маршрутизации,
а не песочница: нельзя обходить отказ через другую оболочку, инструмент
или агента. Степень защиты зависит от среды и активности hooks.

## Инструменты задач в разных средах

Pi предоставляет `task_status`, `ensure_task_repo`, `remove_task_lane`,
`teardown_task_repo`, `checkpoint_commit`. Claude Code и Codex вызывают
общее ядро через `agent-kit task <op> '<json>'`: `status`, `ensure`,
`remove-lane`, `teardown`, `commit`. Вход и выход CLI имеют формат JSON.
[Контракт ядра и операций](../extensions/task-workspace/README.md).

В Pi запуск владельца проверяет готовность, ограничивает время работы и
проверяет итоговое состояние Git. Вопрос владельца возвращается основной
сессии как `needs_input`. В Claude Code нет такого протокола Pi: владелец
возвращает `blocked`, основная сессия отвечает через `SendMessage` и сама
проверяет Git-факты. У Codex тоже нет Pi deadline, lease или доверенного
конверта `git_facts`; используется нативное делегирование.
[Ограничения Claude Code](adr/adr-0008.md), [процесс Codex](codex.md#нативный-рабочий-процесс).

## Инструменты Pi

- [`task-workspace`](../extensions/task-workspace/README.md) управляет
  worktree, коммитами и защитой основного checkout.
- [`subagents`](../extensions/subagents/README.md) предоставляет `subagent`
  с операциями `spawn`, `status`, `steer`, `follow_up`, `wait`, `result`,
  `respond`, `cancel`. Режим `workspace` запускает владельца с дедлайном
  и проверкой результата; `/subagents [kill-all]` управляет запусками.
- `/subagent-role` связывает роли `explore`, `helper`, `review`, `owner`
  с моделями в `subagent-roles.json`. Явный `model=provider/id[:thinking]`
  выбирает модель конкретного запуска. Модель сессии выбирается отдельно
  штатными средствами Pi, включая `enabledModels`.
- [`ask`](../extensions/ask/README.md) задаёт вопросы в интерфейсе Pi
  или через RPC. Без интерфейса возвращает отказ, у субагента направляет
  вопрос основной сессии.
- [`todo`](../extensions/todo/README.md) ведёт фазы и список задач,
  показывает виджет и напоминания; команда `/todo`.
- [`web-search`](../extensions/web-search/README.md) предоставляет
  `web_search` через ChatGPT Codex после `/login openai-codex`.
- [`session-title`](../extensions/session-title/README.md) задаёт имя
  сессии и заголовок терминала по первому запросу с помощью недорогой модели.
- [`footer`](../extensions/footer/index.ts) показывает модель, thinking,
  ветку, стоимость и заполненность контекста; команда `/footer`.
- [`perf-stats`](../extensions/perf-stats/index.ts) показывает время
  до первого токена, скорость, токены и чтения кеша под ответом.
- [`continue-shortcut`](../extensions/continue-shortcut/README.md)
  превращает `.` или `c` в скрытую команду продолжения незаконченной работы.
- [`update-check`](../extensions/update-check/index.ts) сообщает при старте,
  если клон отстал от upstream или находится не на основной ветке.
- [`proxy`](../extensions/proxy/proxy-lib.ts) и `proxy-toggle.ts`
  задают `/proxy on|off|status`, берут адрес из `PI_PROXY` и передают
  настройки живым субагентам.
- [`agent-events`](../extensions/agent-events/README.md) передаёт
  телеметрию жизненного цикла в Warp через OSC 777.

Субагенты запускаются как `pi --mode rpc --no-extensions` со своим
bridge-расширением; остальные расширения в них не загружаются.

## Дополнительные навыки

Навыки из `skills/` ссылаются друг на друга как `skill://<name>`.
Для работы над интерфейсами инструкции предполагают отдельно установленные
`interface-design` и `design-taste-frontend`. Установщик agent-kit их
не поставляет. Навык `fleet` находится в отдельном репозитории
[Fleet](https://github.com/kaktusss123/fleet).
