# Рабочий процесс и инструменты Pi

## От спецификации к реализации

В Pi и Claude Code отправьте `/spec <описание задачи>`, затем, после
согласования требований, `/dev`. Это сообщения агенту, не команды оболочки.
В Codex используйте `$spec` и `$dev`.

В режиме `/spec` основная сессия определяет задачу, создаёт или переиспользует
worktree и исследует код в нём. Навыки исследования помогают установить факты,
а `specification` оформляет требования, решения и проверки в `SPEC.md`
каталога задачи. Продуктовый код в этом режиме не меняется.

В режиме `/dev` основная сессия использует спецификацию и обычно назначает
одного субагента-владельца на основной управляемый worktree каждого изменяемого
репозитория. Для отдельных именованных веток `arena` или `swarm` возможны
параллельные владельцы одного репозитория, но не одного физического worktree.
Независимые работы могут идти параллельно. Владелец реализует изменение, проверяет его и создаёт коммит.
Основная сессия читает фактическое состояние Git, решает, нужен ли независимый
ревьюер, и передаёт исправления новому владельцу. Протокол описан в
[`git-task`](../skills/git-task/SKILL.md) и его `references/`.

## Задачи и рабочие деревья

Задачу определяет ветка пользователя или ветка на основе тикета, например
`feat/KEY-123_short_slug`. Без тикета агент спрашивает разрешение на работу
без него, если оно ещё не дано. Явно порученный автономный режим разрешает
работу без тикета только там, где репозиторий не требует настоящий тикет
трекера. Тикет и `base_ref` агент не придумывает: если база не задана явно,
её выбирает runtime; неоднозначную продуктовую базу решает пользователь.

Каталог задачи находится в `~/.agent-kit/tasks/`; корень можно изменить
через `AGENT_TASK_ROOT`. Он содержит управляемые worktree всех участвующих
репозиториев, `SPEC.md` и дополнительные артефакты задачи. Имя каталога
выводится из имени ветки. Основной checkout остаётся нетронутым, даже если
в нём уже есть незакоммиченные изменения.

Владелец репозитория, RepoOwner, меняет только один назначенный worktree.
Основная сессия координирует, проверяет и интегрирует, но не правит репозитории
задачи сама. Прежде чем создавать дополнительный worktree, нужно создать
основной управляемый worktree этого репозитория. Дополнительный worktree той же задачи, lane, нужен для настоящей
второй ветки: например, backport, hotfix, независимого кандидата `arena` или
части работы `swarm`, но не для отдельного запуска тестов. Для каждой ветки
задают имя, отдельный результат и владельца интеграции.

Коммит через `checkpoint_commit` включает ровно перечисленные пути,
запускает Git hooks, отклоняет основной checkout и пути, похожие на секреты.
Сырой `--no-verify` запрещён; отправка коммита не выполняется автоматически.
Владелец может отчитаться `done` только после проверки закоммиченного
кандидата. Последующая правка требует нового коммита и финальной проверки.
[Граница проверки и гарантии runtime](architecture.md#граница-проверки).

Git shim в `PATH` блокирует изменяющие Git-команды в основном checkout
репозитория с управляемыми worktree, `--no-verify` и перенаправление через
`--git-dir`/`--work-tree`. Отдельная проверка запрещает инструментам записи
менять отслеживаемые файлы основного checkout. Это защита маршрутизации,
а не песочница: нельзя обходить отказ через другую оболочку, инструмент
или агента. Степень защиты зависит от среды и активности hooks.

## Инструменты задач в разных средах

Pi предоставляет `task_status`, `ensure_task_repo`, `remove_task_lane`,
`teardown_task_repo`, `checkpoint_commit`. Claude Code и Codex вызывают
общее ядро через `agent-kit task <op> '<json>'`: `status`, `ensure`,
`remove-lane`, `teardown`, `commit`. Вход и выход CLI имеют формат JSON.
[Контракт ядра и операций](../extensions/task-workspace/README.md).

В Pi запуск владельца проверяет готовность, ограничивает время работы и
проверяет итоговое состояние Git. Вопрос владельца возвращается основной
сессии как `needs_input`. В Claude Code нет такого протокола Pi: владелец
возвращает `blocked`, основная сессия отвечает через `SendMessage` и сама
проверяет Git-факты. У Codex тоже нет Pi deadline, lease или доверенного
конверта `git_facts`; используется нативное делегирование.
[Контракт Claude Code](../skills/git-task/references/claude-code/repo-owners.md),
[процесс Codex](codex.md#нативный-рабочий-процесс).

## Инструменты Pi

- [`task-workspace`](../extensions/task-workspace/README.md) управляет
  worktree, коммитами и защитой основного checkout.
- [`subagents`](../extensions/subagents/README.md) предоставляет `subagent`
  с операциями `spawn`, `status`, `steer`, `follow_up`, `wait`, `result`,
  `respond`, `cancel`. Режим `workspace` запускает владельца с дедлайном
  и проверкой результата; `/subagents [kill-all]` управляет запусками.
- `/subagent-role` связывает роли `explore`, `helper`, `review`, `owner`
  с моделями в `subagent-roles.json`. Явный `model=provider/id[:thinking]`
  выбирает модель конкретного запуска. Модель сессии выбирается отдельно
  штатными средствами Pi, включая `enabledModels`.
- [`ask`](../extensions/ask/README.md) задаёт вопросы в интерфейсе Pi
  или через RPC. Без интерфейса возвращает отказ, у субагента направляет
  вопрос основной сессии.
- [`todo`](../extensions/todo/README.md) ведёт фазы и список задач,
  показывает виджет и напоминания; команда `/todo`.
- [`skill-reflection`](../extensions/skill-reflection/README.md) примерно каждые
  восемь пользовательских сообщений добавляет скрытый совет применить `reflect`
  к действительно прочитанным навыкам текущей ветки сессии. Отдельного запроса
  модели, автоматической правки файлов или постоянного отчёта пользователю нет.
  В субагентах напоминание выключено; в Claude Code и Codex этого hook нет.
- [`web-search`](../extensions/web-search/README.md) предоставляет
  `web_search` через ChatGPT Codex после `/login openai-codex`.
- [`session-title`](../extensions/session-title/README.md) задаёт имя
  сессии и заголовок терминала по первому запросу с помощью недорогой модели.
- [`footer`](../extensions/footer/index.ts) показывает модель, thinking,
  ветку, стоимость и заполненность контекста; команда `/footer`.
- [`perf-stats`](../extensions/perf-stats/index.ts) показывает время
  до первого токена, скорость, токены и чтения кеша под ответом.
- [`continue-shortcut`](../extensions/continue-shortcut/README.md)
  превращает `.` или `c` в скрытую команду продолжения незаконченной работы.
- [`update-check`](../extensions/update-check/index.ts) сообщает при старте,
  если клон отстал от upstream или находится не на основной ветке.
- [`proxy`](../extensions/proxy/proxy-lib.ts) и `proxy-toggle.ts`
  задают `/proxy on|off|status`, берут адрес из `PI_PROXY` и передают
  настройки живым субагентам.
- [`agent-events`](../extensions/agent-events/README.md) передаёт
  телеметрию жизненного цикла в Warp через OSC 777.

Субагенты запускаются как `pi --mode rpc --no-extensions` со своим
bridge-расширением; остальные расширения в них не загружаются.

## Автономная доставка и повторное ревью

Один навык [`full-send`](../skills/full-send/SKILL.md) обслуживает два режима.
Достаточно обычного поручения: «Реализуй согласованное изменение, full send»
или «Подготовь этот MR, full-stop». Обязательного slash нет. Цитата,
обсуждение режимов или задание написать сам навык не запускают доставку;
помощник с ограниченным поручением не наследует полномочия из фонового текста.

- **full send**: реализация, проверки, независимое ревью, отправка своей ветки,
  создание или обновление PR/MR, обработка относящихся к задаче проверок и
  замечаний, затем слияние по обычной политике репозитория. Завершение —
  подтверждённое сервером `MERGED`, а не включённый auto-merge или очередь.
- **full stop**: те же шаги до готового открытого PR/MR, но без слияния,
  auto-merge или очереди. Агент может отключить существующий auto-merge и
  убрать из очереди только свой PR/MR, проверяя состояние перед отправкой
  нового head и передачей результата. Итог — `READY`,
  `WAITING FOR REQUIRED APPROVAL` или `BLOCKED` с фактическими причинами.

Повторных вопросов по уже порученным обычным шагам нет: агент сам получает
доступные факты и выбирает консервативные обратимые действия. Настоящие
блокеры остаются: недоступная возможность, неоднозначная цель или база,
непроверяемое обязательное поведение, действие за пределами поручения.
Режимы не обходят Git hooks, защиту веток, одного владельца worktree,
обязательный трекер или разрешения среды. Production, удаление данных,
чужие ветки и установка в активную среду не входят в скрытые полномочия;
последствия push/merge для production проверяются до действия.

[`code-review`](../skills/code-review/SKILL.md) включает необязательный
[`review-loop`](../skills/code-review/references/review-loop.md): по умолчанию
до трёх раундов вместе с первым. Исправления идут через владельца, ревьюеры
читают фиксированный кандидат. Исчерпанный бюджет не означает одобрения.

[`council`](../skills/council/SKILL.md) собирает независимые оценки выбранных
пользователем моделей по общей шкале 1–10. Нужны модели и желаемый порог;
провайдеры и число участников не зашиты. Сходимость требует оценки **каждого**
обязательного участника не ниже порога на текущих точных base/head,
без открытых подтверждённых блокеров и неуспешных или неизвестных обязательных
проверок. Среднее не используется; число субъективно и не заменяет доказательства.
Недоступная модель не подменяется, старые или отсутствующие оценки не засчитываются.
По умолчанию также три раунда; отдельного вложенного цикла на каждого участника нет.

[`modernize`](../skills/modernize/SKILL.md) сначала восстанавливает цель старого
PR/MR и проверяет, нужен ли он на нынешней базе: `MODERNIZE`, `REWORK` или
`CLOSE`. Чистый rebase не доказывает актуальность идеи. Одна просьба оценить
остаётся чтением; рекомендация `CLOSE` не разрешает закрытие, а модернизация
не включает доставку или слияние автоматически.

Эти инструкции переносимы, но возможности среды различаются: выбранные модели
и ожидание должны реально поддерживаться текущим хостом. Установка и
статические проверки доказывают упаковку и текстовый контракт, не выполнение
инструкций моделью в реальной задаче.

## Дополнительные навыки

[`arena`](../skills/arena/SKILL.md) сравнивает независимые попытки одной задачи
по заранее заданным критериям; [`swarm`](../skills/swarm/SKILL.md) распределяет
разные части работы и сводит покрытие и пробелы. Оба применимы к исследованию
без записи. Для записи нужны именованные управляемые ветки с отдельными
владельцами и заранее назначенная интеграция.

[`correct`](../skills/correct/SKILL.md) полезен после отклонённого отчёта,
даже если пользователь не наблюдал исполнение. Например: «В отчёте написано,
что проверки прошли, но это неверно. Разбери ошибку по результатам выполнения».
Навык сам исследует доступные свидетельства и не превращает одну жалобу
в автоматическое переписывание репозитория.
[`reflect`](../skills/reflect/SKILL.md) разбирает текущую сессию и предлагает
точные улучшения реально использованных навыков. Совет расширения не даёт
права записи; уже согласованные точные правки не требуют повторного одобрения.

[`verification-design`](../skills/verification-design/SKILL.md) помогает создать
проектный навык проверки с `SKILL.md`, `features/README.md` и исполнимыми
сценариями. Он создаётся для конкретного проекта, а не устанавливается готовым
для всех. Карта самого agent-kit находится в
[`.agents/skills/verify/`](../.agents/skills/verify/SKILL.md); в Claude Code
этот файл нужно прочитать явно. Проверки выбирают по затронутому поведению,
а не запускают всю карту при каждой правке.

[`benchmark-checklist`](../skills/benchmark-checklist/SKILL.md) проверяет
корректность измеряемой работы и сопоставимость замеров;
[`formal-verification`](../skills/formal-verification/SKILL.md) ограничивает
формальную проверку одним свойством с явной связью модели и кода.
[Источники идей и уведомление MIT](attribution.md).

Навыки из `skills/` ссылаются друг на друга как `skill://<name>`.
Для работы над интерфейсами инструкции предполагают отдельно установленные
`interface-design` и `design-taste-frontend`. Установщик agent-kit их
не поставляет. Навык `fleet` находится в отдельном репозитории
[Fleet](https://github.com/kaktusss123/fleet).
