# Codex CLI

Поддерживается рабочий процесс Codex CLI 0.166.0: общие навыки, правила общения
и Git, `$spec` / `$dev`, нативное делегирование, `agent-kit task` и защитные
`PreToolUse` hooks. Это не перенос интерфейса и расширений Pi.

```sh
agent-kit install codex
agent-kit status
agent-kit update
agent-kit uninstall codex
```

Именованный `install` добавляет Codex к сохранённому выбору. Существующий выбор
Pi/Claude не расширяется сам; свежая установка без выбора включает все три
среды. `update` обновляет checkout через `git pull --ff-only`, затем восстанавливает
ссылки только выбранных сред. Обновление правил требует `install`/`update`:
объединённый файл не меняется вслед за редактированием исходников сам.

## Две области владения

| Файл состояния в `$XDG_STATE_HOME/agent-kit` | Корень назначения | Пути |
| --- | --- | --- |
| `links-codex.tsv` | `${CODEX_HOME:-$HOME/.codex}` | `AGENTS.md`, `hooks.json` |
| `links-codex-skills.tsv` | `$HOME/.agents` | `skills/<name>` |

Если `XDG_STATE_HOME` не задан, база — `$HOME/.local/state`. Формат каждого файла
тот же: `<относительный путь> TAB <абсолютный источник>`. Файлы Pi (`links.tsv`)
и Claude (`links-claude-code.tsv`) принадлежат отдельным корням. Относительные
пути никогда не содержат обхода `..`; генерация не разрешает произвольные
источники. Каждый корень задаётся явно, а не через переходы между каталогами.
Записи интерпретируются относительно текущего корня:
перед сменой HOME/CODEX_HOME удалите установку в прежнем корне отдельно, если
она больше не нужна. Установщик не разыскивает и не удаляет прежние корни.

Навыки — отдельные симлинки; установщик не владеет каталогом `.agents` целиком.
`CODEX_HOME` не переносит общие навыки. Не создаётся копия в `$CODEX_HOME/skills`.
Соседние поставки сохраняют свои имена и своё владение.

`AGENTS.md` генерируется из тонкой привязки `rules/codex.md` (первой) и общих
`rules/AGENTS.md` без ручного копирования правил. `hooks.json` содержит команду
адаптера из выбранного checkout с корректным экранированием путей. Оба файла
сохраняются как проверяемые по содержимому неизменяемые артефакты
`<state>/generated-codex/<sha256>-<name>`, а в корень Codex ставятся симлинки.
Эти два источника конструируются отдельным кодом, не разрешением произвольных
внешних источников в общем валидаторе. Изменённый артефакт не перезаписывается:
установка отказывается с диагностикой. При изменении исходников или checkout
создаётся новое содержимое; только ссылка, совпадающая с записанным владением,
перенаправляется. Старые артефакты намеренно остаются: автоматического удаления
неучтённых источников нет. `uninstall codex` удаляет лишь точно совпадающие
учтённые ссылки назначения, а не чужие файлы или всё хранилище артефактов.

Чужие `AGENTS.md`, `hooks.json`, навыки и перенаправленные пользователем ссылки
сохраняются; конфликт даёт код 1. `AGENTS.override.md`, включая оборванный симлинк,
диагностируется как затенение общих правил: установка возвращает 1 и `status`
явно сообщает, что правила неактивны. Hooks устанавливаются независимо от
затенения правил, если их собственный путь свободен/принадлежит agent-kit.
`config.toml`, учётные данные и разрешения доверия не изменяются.

## Активация и пределы защиты

После установки проверьте и явно одобрите сторонние hooks через `/hooks`.
Установщик не обходит проверку доверия. Существование `hooks.json` и успешная
установка не доказывают, что Codex выполняет hooks.

Протокол привязан к
[официальному тегу rust-v0.166.0](https://github.com/openai/codex/tree/rust-v0.166.0):
`codex-rs/hooks/src/events/pre_tool_use.rs`,
`codex-rs/core/src/tools/handlers/unified_exec/exec_command.rs` и
`codex-rs/core/src/tools/handlers/apply_patch.rs`.

- Shell-команда приходит как `tool_name: Bash`, `tool_input.command`.
  Адаптер возвращает `permissionDecision: allow` и `updatedInput.command`,
  добавляя экспорт окружения существующего Git shim перед исходной командой.
  Не используется ни SessionStart, ни `CLAUDE_ENV_FILE`.
- Shim классифицирует фактические аргументы и рабочий каталог Git после `cd`,
  `git -C` и обычных вложенных shell, запрещая изменение основного checkout
  при наличии управляемого рабочего дерева и сырой `--no-verify` везде.
- Нативный `apply_patch` тоже передаёт `tool_input.command`. Проверяются все
  `Add/Update/Delete File` и оба конца `Move to`, включая относительные пути,
  по фактическому `input.cwd`. Запрет — явный `hookSpecificOutput` с
  `hookEventName: PreToolUse`, `permissionDecision: deny` и причиной.
- Некорректные входные данные/ошибки адаптера по возможности превращаются в
  явный запрет. Но Codex может продолжить после ошибки самого hook-процесса
  или таймаута; отключённые/недоверенные hooks вообще не выполняются.

Это защита от ошибки маршрутизации, не изоляция произвольного кода. Абсолютный
путь к Git, сброс PATH во вложенной оболочке, произвольная shell-запись файла
и последующий `write_stdin` не дают гарантированной границы защиты. Во всех
случаях вручную направляйте записи в абсолютный путь управляемого рабочего
дерева, используйте `git -C <worktree>` и `agent-kit task commit`. После работы
сверяйте, что основной checkout не изменён. Запрет нельзя обходить другим
инструментом или агентом.

## Нативный рабочий процесс

Вызывайте `$spec` / `$dev`. Прямые привязки доступны до ссылок на Pi:
[task/delegation](../skills/git-task/references/codex/workflow.md) и
[checkpoint](../skills/git-commit/references/codex/checkpoint.md).
Ядро CLI не требует Pi SDK. Контроллер назначает одного владельца на репозиторий,
использует доступные нативные инструменты агентов, а после завершения сам читает
HEAD, ветку и чистоту дерева. У Codex нет Pi lease, deadline, отчётного инструмента
или доверенного конверта `git_facts`. Отсутствие делегирования блокирует реализацию,
а не разрешает писать в основной checkout.

## Проверки без реальной установки и модели

```sh
node --test tests/codex/*.test.mjs
tests/installer/run.sh
tests/layout/run.sh
tests/skills/run.sh
tests/snapshot/run.sh
```

Проверки используют временные HOME/корни; hook-фикстуры создают
репозиторий под локальным `node_modules`, поскольку `/tmp` ядро намеренно считает
разрешённым временным пространством. Они проверяют реальный stdin/stdout адаптера,
выполняют переписанные shell-команды и сверяют запреты/разрешения. Проверка
`discovery.test.mjs` при установленном Codex 0.166.0 запускает только
`codex debug prompt-input`, без модели и сети: наблюдает общие правила и нативное
обнаружение навыков через симлинки при отдельном CODEX_HOME. При отсутствии этой
версии проверка явно пропускается. Это не проверка живого вызова hooks самим
Codex: для неё нужен отдельно изолированный сеанс с явным доверием временным
hooks; установочные/протокольные фикстуры не заменяют такого наблюдения.
